## 2. 주요 설정값

### 2-1. JVM

실행 옵션은 `backend/Dockerfile`의 `ENTRYPOINT`에 있다.

```
java -XX:MaxHeapSize=1g -XX:InitialHeapSize=256m -jar /app/app.jar
```

- 힙 상한을 절대값으로 고정한다. 상한이 없으면 JVM이 컨테이너가 아니라 호스트 메모리를 기준으로
  최대 힙을 잡아, MySQL 버퍼풀·Jenkins·모니터링 스택과 겹칠 때 전체가 빠듯해진다.
- 컨테이너 메모리 상한은 compose의 `mem_limit`으로 따로 건다 (backend 1536m).
- 비루트(uid 10001)로 실행하고 `cap_drop: ALL`을 적용한다.
- 컨테이너 HEALTHCHECK: `curl -fsS http://localhost:8080/api/health`
  (interval 15s / timeout 5s / start-period 60s / retries 5)

프로파일링이 필요할 때만 `infra/.env`의 `JFR_OPTS`로 `JAVA_TOOL_OPTIONS`를 주입한다.
평소에는 비어 있어 아무 영향이 없다. 절차는 `infra/docs/profiling.md`.

### 2-2. WAS (내장 Tomcat)

| 항목 | 값 | 비고 |
| --- | --- | --- |
| 포트 | 8080 | 외부 미노출. nginx가 `/api/`로만 프록시 |
| 최대 스레드 | Spring Boot 기본값 (200) | 별도 지정하지 않았다 |
| MBean 레지스트리 | `server.tomcat.mbeanregistry.enabled: true` | 켜야 `tomcat_threads_busy_threads` 지표가 나온다 |
| `spring.jpa.open-in-view` | `false` | |

### 2-3. DB 커넥션 풀 (HikariCP)

별도 설정이 없어 Spring Boot 기본값(최대 10)을 쓴다. 부하 테스트에서 확인한 병목은
커넥션 풀이 아니라 호스트 CPU였다 (`infra/docs/load-test-summary.md`).

JDBC URL에는 PreparedStatement 캐시 옵션을 붙인다 (`infra/docker-compose.yml`의 `DB_URL`).

```
cachePrepStmts=true&prepStmtCacheSize=250&prepStmtCacheSqlLimit=2048&useServerPrepStmts=true
```

### 2-4. 웹서버 (Nginx)

설정 파일: `infra/nginx/conf.d/default.conf`

| 항목 | 값 |
| --- | --- |
| 리스닝 | 80(HTTPS로 301), 443 (`http2 on`) |
| TLS | TLSv1.2 / TLSv1.3, 세션 캐시 10m, 세션 티켓 off |
| 인증서 | `/etc/letsencrypt/live/j15d105.p.ssafy.io/{fullchain,privkey}.pem` |
| 보안 헤더 | HSTS `max-age=86400`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin` |
| 레이트 리밋 | `/api/v1/auth/(login\|signup)` 20 req/분(burst 10), 그 외 `/api/` 20 req/초(burst 40). 초과 시 429 |
| 업로드 상한 | `client_max_body_size 20m` (`/api/`), 10m (Jenkins 웹훅) |
| 프록시 타임아웃 | `proxy_read_timeout 60` (Grafana만 300) |
| 차단 경로 | `/actuator/` → 404, `/jenkins/` → 403 (웹훅 경로 `/jenkins/project/`만 허용) |
| 기타 | `server_tokens off`, `resolver 127.0.0.11` (업스트림을 요청 시점에 해석) |

### 2-5. MySQL

`infra/docker-compose.yml`의 `command`로 지정한다.

| 항목 | 값 |
| --- | --- |
| 문자셋 | `utf8mb4` / `utf8mb4_unicode_ci` |
| InnoDB 버퍼풀 | 2G |
| 슬로우 쿼리 로그 | ON, `long_query_time=1`, `/var/lib/mysql/slow.log` |
| 타임존 | `Asia/Seoul` |
| 컨테이너 메모리 상한 | 3g |
| 포트 | 외부 미노출 (컨테이너 네트워크 전용) |

### 2-6. Redis

| 항목 | 값 |
| --- | --- |
| 인증 | `requirepass ${REDIS_PASSWORD}` |
| 영속화 | `appendonly yes` |
| 메모리 | `maxmemory 512mb`, `maxmemory-policy allkeys-lru` |
| 컨테이너 메모리 상한 | 768m |
| 포트 | 외부 미노출 |

용도는 AI 코치 응답 캐시·대화 세션·호출 상한, 쓰기 API 재전송 방지(Idempotency)다.

### 2-7. 컨테이너 공통

- 전 서비스 `restart: unless-stopped`, `security_opt: no-new-privileges:true`
- 서비스별 `mem_limit` 지정 (한 서비스가 폭주해도 다른 서비스를 굶기지 않게)
- Docker 로그 로테이션: `/etc/docker/daemon.json`에 `max-size 10m`, `max-file 3`

## 3. 빌드 시 사용되는 환경 변수

### 3-1. Backend

Spring Boot는 `.env`를 자동으로 읽지 않는다. 운영 서버에서는 `infra/.env`의 값을
`infra/docker-compose.yml`이 컨테이너 환경 변수로 전달한다. 로컬에서는 셸이나 IDE 실행 구성에 넣는다.

| 환경 변수 | 설명 | 필수 |
| --- | --- | --- |
| `DB_URL` / `DB_USERNAME` / `DB_PASSWORD` | MySQL 접속 정보 | 필수 |
| `REDIS_HOST` / `REDIS_PORT` / `REDIS_PASSWORD` | Redis 접속 정보 | 필수 |
| `CORS_ALLOWED_ORIGINS` | 허용 Origin, 쉼표 구분 | 필수 |
| `JWT_SECRET` | Access Token 서명키. **32바이트 미만이면 기동 실패** | 필수 |
| `DATA_ENCRYPTION_KEY` | `*_encrypted` 컬럼 AES-256-GCM 키. Base64 32바이트. **잃으면 복구 불가** | 필수 |
| `DATA_HASH_KEY` | 이메일·`userKey` 조회용 HMAC 키. Base64 32바이트 | 필수 |
| `NUMBER_HASH_KEY` | 계좌·카드번호 `*_hash` HMAC 키. **바꾸면 기존 해시와 매칭이 깨진다** | 필수 |
| `SSAFY_FINANCE_API_KEY` | SSAFY 금융망 API Key | 필수 |
| `FCM_SERVICE_ACCOUNT_PATH` | Firebase 서비스 계정 JSON 경로 | prod 필수 |
| `OPENAI_API_KEY` | SSAFY GMS 중계 토큰. 비우면 AI 코치가 템플릿 문장으로 응답 | prod 필수 / local 선택 |
| `GOOGLE_CLIENT_ID` | 구글 ID token `aud`로 허용할 클라이언트 ID. **비우면 구글 로그인 503** | 선택 |
| `KAKAO_APP_ID` | 카카오 앱 ID(숫자). 비우면 앱 ID 대조만 생략 | 선택 |
| `JFR_OPTS` | JFR 프로파일링 옵션. 평소 비움 | 선택 |

인프라 전용 변수 (`infra/.env`에만 있고 백엔드에는 전달되지 않는다):

| 환경 변수 | 설명 |
| --- | --- |
| `DOCKER_GID` | EC2의 docker 그룹 GID. `getent group docker \| cut -d: -f3` |
| `APP_DIR` | EC2 배포용 체크아웃 경로 (기본 `/home/ubuntu/app`) |
| `MYSQL_ROOT_PASSWORD` / `MYSQL_DATABASE` / `MYSQL_USER` / `MYSQL_PASSWORD` | MySQL 초기화 |
| `MYSQL_EXPORTER_PASSWORD` | mysqld-exporter 전용 DB 계정 비밀번호 |
| `GRAFANA_ADMIN_USER` / `GRAFANA_ADMIN_PASSWORD` | Grafana 관리자 계정 |
| `MATTERMOST_WEBHOOK_URL` | 배포 실패·서비스 이상 알림 |

> `infra/scripts/check-env.sh`가 배포 전에 `.env`를 검사한다.
> 중복 정의, 주석(`#`)에 잘려 빈 값이 된 항목, `docker-compose.yml`·`application*.yml`이
> 참조하는데 `.env`에 없는 키를 잡는다.

### 3-2. Frontend

`EXPO_PUBLIC_` 접두사가 붙은 값은 **빌드 결과물에 포함되는 공개 설정**이다.
Client Secret·토큰·비밀번호는 넣지 않는다.

| 환경 변수 | 설명 | 필수 |
| --- | --- | --- |

| `EXPO_PUBLIC_ENABLE_DEMO_LOGIN` | 릴리스 빌드에서 개발용 로그인 노출 여부(`"true"`일 때만) | preview APK 시연 시 |

| 프로필 | 산출물 | `EXPO_PUBLIC_API_BASE_URL` | 개발용 로그인 |
| --- | --- | --- | --- |
| `development` | 개발 클라이언트(내부 배포) | `https://j15D105.p.ssafy.io/api` | `true` |
| `preview` | APK(내부 배포) | `https://j15D105.p.ssafy.io/api` | `true` |

## 4. 빌드와 배포

### 4-1. 클론

```bash
git clone <GitLab 프로젝트 URL> app
cd app
```

모노레포다. `backend/`, `frontend/`, `infra/`가 한 저장소에 있다.

### 4-2. 서버 스택 기동 (최초 1회)

```bash
cd app/infra
cp .env.example .env     # 값 채워넣기 (커밋 금지)
docker compose up -d
```

- `.env`의 `DOCKER_GID`는 EC2에서 `getent group docker | cut -d: -f3`로 확인한다.
- FCM을 쓰면 서비스 계정 JSON을 `infra/secrets/fcm-service-account.json`에 둔다.
- TLS 인증서 최초 발급은 `infra/README.md`를 따른다. 이후 갱신은 certbot 컨테이너가 자동으로 한다.

### 4-3. 백엔드 빌드

빌드와 테스트는 **`backend/Dockerfile`의 builder 스테이지 안에서** 수행된다.
Jenkins 컨테이너에 JDK 21과 Gradle이 없고, DooD 환경에서 워크스페이스 경로가 호스트와 달라
`docker.inside` 방식이 맞지 않기 때문이다.

```bash
# 서버(컨테이너) 빌드 — 테스트 포함
docker compose -f infra/docker-compose.yml --env-file infra/.env build backend
```

로컬에서 직접 빌드·실행할 때는 `backend/`에서 Wrapper를 쓴다. Gradle을 따로 설치하지 않는다.

```bash
./gradlew clean build                                    # 테스트 포함
./gradlew bootRun --args='--spring.profiles.active=local'
```

테스트는 `test` 프로필(H2 인메모리)로 돌아 외부 MySQL·Redis·외부 API가 필요 없다.

### 4-4. 자동 배포 (기본 경로)

`develop`에 머지되면 GitLab 웹훅이 Jenkins를 호출하고, 파이프라인이 끝까지 자동으로 진행한다.

```
develop 머지 → GitLab Webhook → Jenkins
  ① Checkout
  ② Build & Test   (backend 이미지 빌드 = gradle clean build, 실패 시 배포하지 않음)
  ③ Deploy         (infra/scripts/deploy.sh)
```

`deploy.sh`가 하는 일:

1. `infra/scripts/check-env.sh`로 `.env` 사전 검사
2. `$APP_DIR`을 `git reset --hard`로 origin 기준에 맞춤
3. 이미지 빌드 후 대상 서비스 재기동
4. 헬스체크 2단계 → 실패하면 직전 이미지로 롤백
5. Mattermost 알림 (실패 시, 그리고 실패 후 복구됐을 때만)

파이프라인 정의는 저장소 루트 `Jenkinsfile`, 상세 흐름은 `infra/docs/ci-cd.md`.

### 4-5. 앱 빌드 (APK)

```bash
cd frontend
npm ci
npx eas login
npx eas build -p android --profile preview
```

로컬 개발 실행은 `cp .env.example .env`로 값을 채운 뒤 `npm start` / `npm run android`.

## 5. 배포 시 특이사항

여기 적힌 것은 전부 이 프로젝트에서 실제로 겪은 일이다. 경위는 `infra/todo/jiw/day-XX.md`에 있다.

### 5-1. 배포 대상에서 `jenkins`를 제외한다

배포 스크립트가 **Jenkins 컨테이너 안에서** 실행되므로, 배포 대상에 jenkins를 넣으면
자기 자신을 재시작해 빌드가 죽는다. 같은 이유로 compose에 `depends_on: jenkins`를 걸어서도 안 된다
(2026-09-07 실제로 발생). Jenkins 이미지를 바꿨을 때만 호스트에서 수동으로 올린다.

```bash
cd ~/app/infra && docker compose up -d --build --no-deps jenkins
```

### 5-2. 배포 대상에는 모니터링 서비스를 반드시 포함한다

`DEPLOY_SERVICES`에서 빠지면, 설정 파일이나 이미지 태그를 고쳐 머지해도 배포가 반영하지 않는다.
수동으로 올린 변경은 다음 배포의 `git reset --hard`에 밀려 조용히 원복된다.

### 5-3. 헬스체크는 2단계다

`/actuator/health`(DataSource·Redis 포함) → `/api/health`(외부 경로) 순으로 본다.
`/api/health`는 앱 컨트롤러라 의존성을 보지 않으므로, 그것만 검사하면
**DB에 못 붙은 배포가 성공으로 처리된다.**

### 5-4. 롤백 지점은 healthy일 때만 갱신한다

이미지 태그는 세 개다. `infra-backend:latest`(방금 빌드) / `:deployed`(헬스체크를 통과한 마지막) /
`:rollback`(롤백 지점). 현재 컨테이너가 비정상일 때 그 이미지를 롤백 지점으로 잡으면,
롤백해도 같은 깨진 이미지가 다시 뜬다(2026-09-14 실측).

### 5-5. `$APP_DIR`에서 코드를 고치지 않는다

`/home/ubuntu/app`은 **배포 대상 사본**이다. 매 배포마다 `git reset --hard`로 덮어쓴다.
`.env` 등 gitignore된 파일만 보존된다.

### 5-6. `docker compose down -v`를 실행하지 않는다

명명 볼륨(`mysql_data`, `jenkins_home`, `grafana_data`, `prometheus_data`, `loki_data`)이 전부 삭제된다.
DB 전체, Jenkins job·자격증명, 대시보드와 지표·로그 이력이 함께 사라진다.

### 5-7. 병합 시 `docker-compose.yml`의 `environment:` 블록을 확인한다

2026-09-08에 `develop` 병합 과정에서 `JWT_SECRET` 등 4줄이 유실되어 백엔드가 기동하지 못했다
(`app.auth.jwt.secret must be at least 32 bytes`). 인프라 파일을 여러 MR이 동시에 건드릴 때
충돌 해소로 사라지기 쉽다.

### 5-8. Flyway는 `out-of-order: true`로 운영한다

마이그레이션 번호를 담당 영역별 구간(V1~V9 / V10~)으로 나눠 써서, 이미 V13이 적용된 DB에
나중에 V4가 추가되는 일이 정상이다. 이 옵션이 없으면 기동이 막힌다.

또한 **빈 DB에 V1부터 번호순으로 적용하면 V6에서 멈춘다.** V6의 `transaction.card_id`가
V11의 `card`를 FK로 참조하기 때문이다(Error 1824). 빈 DB에서 시작한다면
V1~V5, V7~V11을 먼저 적용한 뒤 `out-of-order`로 나머지를 적용하거나, 아래 DB 덤프로 시작한다.

### 5-9. Prometheus 설정은 디렉터리로 마운트한다

단일 파일로 마운트하면 컨테이너가 기동 시점의 inode를 잡고 있어서,
배포의 `git reset --hard`가 파일을 새로 만들면 리로드가 성공해도 옛 내용을 계속 본다.

### 5-10. Grafana 대시보드는 코드로 프로비저닝된다

`infra/monitoring/grafana/provisioning/dashboards/`의 JSON이 원본이다.
Grafana UI에서 고친 것은 컨테이너 재생성 시 사라진다.

### 5-11. Jenkins UI는 외부에 열지 않는다

Jenkins 컨테이너는 `docker.sock` 접근권을 가져 뚫리면 호스트 전체가 넘어간다.
UI는 루프백(`127.0.0.1:8080`)에만 바인딩하고 SSH 터널로 접근한다.

```bash
ssh -L 8080:127.0.0.1:8080 ssafy-ec2   # 이후 http://localhost:8080/jenkins/
```

## 6. DB 접속 정보와 주요 계정

**실제 값은 저장소에 없다.** 아래는 계정의 종류와 값이 정의된 위치다.

### 6-1. 데이터베이스

| 항목 | 값 | 정의 위치 |
| --- | --- | --- |
| DBMS | MySQL 8.0 (컨테이너 `mysql`) | `infra/docker-compose.yml` |
| 접속 주소 | `mysql:3306` (컨테이너 네트워크 전용, 외부 포트 없음) | 동일 |
| 스키마 | `dodam` (`utf8mb4` / `utf8mb4_unicode_ci`) | `infra/.env`의 `MYSQL_DATABASE` |
| 앱 계정 | `dodam` | `infra/.env`의 `MYSQL_USER` / `MYSQL_PASSWORD` |
| root 계정 | `root` | `infra/.env`의 `MYSQL_ROOT_PASSWORD` |
| 지표 수집 계정 | `exporter` (PROCESS, REPLICATION CLIENT, performance_schema SELECT만) | `infra/.env`의 `MYSQL_EXPORTER_PASSWORD`, 생성 SQL은 `infra/docs/monitoring.md` |
| JDBC URL | `jdbc:mysql://mysql:3306/${MYSQL_DATABASE}?...` | `infra/docker-compose.yml`의 `DB_URL` |

외부에서 DB에 붙어야 하면 SSH 터널을 쓴다. 포트를 열지 않는다.

### 6-2. 그 밖의 계정

| 대상 | 계정 | 값 위치 |
| --- | --- | --- |
| Redis | 비밀번호만 (`requirepass`) | `infra/.env`의 `REDIS_PASSWORD` |
| Grafana 관리자 | `GRAFANA_ADMIN_USER` | `infra/.env` |
| Jenkins | Jenkins 자체 계정 + Credentials(`gitlab-https`, `ec2-jenkins-deploy`) | Jenkins 내부, EC2 `~/.git-credentials` |
| GitLab 웹훅 secret | — | EC2 `~/.jenkins-webhook-secret` (600) |
| SSAFY 금융망 / GMS / Google / Kakao / FCM / Mattermost | 키·토큰 | `infra/.env`, `infra/secrets/` — 절차는 [외부서비스.md](외부서비스.md) |

### 6-3. 키 취급 주의

| 키 | 주의 |
| --- | --- |
| `DATA_ENCRYPTION_KEY` | `*_encrypted` 컬럼의 AES-256-GCM 키. **잃으면 복구 불가.** DB 덤프와 **다른 장소**에 별도 백업 |
| `DATA_HASH_KEY` | 이메일·`userKey` 조회용 HMAC 키. 바뀌면 조회가 깨진다 |
| `NUMBER_HASH_KEY` | 계좌·카드번호 `*_hash` HMAC 키. 한번 정하면 고정 |
| `JWT_SECRET` | 32바이트 미만이면 기동 실패 |

키와 DB 덤프를 같은 곳에 두면 컬럼 암호화가 무의미해진다. 그래서 DB 백업(`backup.sh`, cron 매일 04:00)과
시크릿 백업(`backup-secrets.sh`, 수동)을 분리해 운영한다. 방침은 `infra/todo/security.md` R5.

## 8. DB 덤프로 시작하기

마이그레이션과 시연 데이터 적재가 끝난 상태의 덤프가 [dodam_dump.sql.gz](dodam_dump.sql.gz)에 있다.

```bash
mysql -u<user> -p -e "CREATE DATABASE dodam CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci"
gunzip -c exec/dodam_dump.sql.gz | mysql --default-character-set=utf8mb4 -u<user> -p dodam
```

- 덤프의 암호화 컬럼은 **덤프 전용 키**로 만들었다. 다른 키로 서버를 띄우면
  계좌·카드번호 복호화와 번호 해시 조회만 실패하고 나머지 기능은 정상이다.
- 현금흐름 예측·패턴 분석·진단 같은 파생 데이터는 덤프에 없다. 앱에서 한 번씩 생성한다.
- 운영 서버에 seed를 다시 적재할 때는 `infra/scripts/seed-load.sh`를 쓴다.
  적재 순서와 선행 조건은 `backend/database/seeds/README.md`에 있다.
