# 물리 스키마 공통 정책

## 민감 식별자 저장

- 계좌번호, 카드번호, OAuth 식별정보, 외부 금융망 userKey, FCM 토큰은 원문 평문을 저장하지 않는다.
- 원문 복원이 필요한 값은 `*_encrypted`, 동일성 조회·중복 확인은 `*_hash`, 화면 표시는 `*_masked` 컬럼을 사용한다.
- `*_encrypted`는 AES-256-GCM의 nonce·ciphertext·tag를 하나의 버전된 binary payload로 저장한다.
- `*_hash`는 암호화 키와 분리된 키를 사용하는 HMAC-SHA-256 결과를 64자리 16진수로 저장한다.
- 암호화 키와 HMAC 키는 DB 및 소스코드 밖의 Secret으로 관리한다.
- API의 `{accountNo}`, `{cardNo}` 입력값은 서버에서 해시한 뒤 `*_hash`로 조회한다.
- Day 1 Seed에는 실제 개인정보나 금융번호를 사용하지 않고 테스트 전용 암호문·해시·마스킹 값을 넣는다.

## 소유권 무결성

- 사용자 리소스끼리 연결할 때는 서비스 계층에서 양쪽의 `user_id`가 같은지 검증한다.
- Card·Subscription·Loan·DepositSaving·Transaction·GoalAccount·Diagnosis·Recommendation·SimulationGoalImpact의 핵심 관계는 DDL의 복합 FK로 동일 사용자를 추가 보장한다.
- MinusAccount와 DepositSaving은 `(user_id, account_id, account_type)` 복합 FK로 실제 Account의 소유자와 하위 유형이 일치하도록 보장한다.
- GoalAccount는 같은 복합 FK와 CHECK로 `MINUS` 계좌 연결을 DB 단계에서 차단한다.
- GoalAccount는 SavingGoal FK를 추가로 사용하여 `SPENDING` 목표에 계좌가 연결되는 것을 차단한다.
- GoalAccount의 `account_id`는 UNIQUE이며 동일 계좌를 여러 목표에 중복 합산하지 않는다.
- Card·Loan·DepositSaving의 출금계좌는 유형을 포함한 복합 FK로 `DEMAND_DEPOSIT`만 허용한다.
- SavingsPayment는 유형을 포함한 복합 FK로 `SAVINGS`에만 연결된다.
- SavingGoal·SpendingGoal과 DailyReport·MonthlyReport는 상위 유형을 포함한 복합 FK로 잘못된 하위 타입 연결을 차단한다.
- nullable 관계는 연결 대상이 없을 수 있지만 값이 존재할 때는 동일 사용자여야 한다.

## 날짜·금액·중복 정책

- 금액, 금리, 일자 범위는 DDL `CHECK` 제약과 애플리케이션 Validation에서 함께 검증한다.
- 카드 결제일, 급여일, 상환일, 적금 납입일은 1~31 범위로 저장하고 말일이 없는 달의 보정은 애플리케이션에서 처리한다.
- CashflowEvent는 `(forecast_id, dedupe_key)`로 동일 예정 이벤트의 중복 반영을 차단한다.
- CashflowEvent 금액은 항상 양수이고 `direction`으로 입금·출금을 구분한다.
- FinancialProduct는 외부 데이터에 `(source_type, company_id, external_product_code)`, 수동·Seed 데이터에 `(company_id, product_type, product_name)`을 식별키로 사용한다.
- Report는 `(user_id, type, period)`당 하나만 생성한다.

## 삭제 및 이력 보존

- User, Goal, Simulation, Notification은 `deleted_at` 기반 소프트 삭제를 사용한다.
- Subscription 삭제 API는 행 삭제가 아니라 `CANCELED` 상태 전이로 처리한다.
- Diagnosis, Recommendation, Improvement, Report와 각종 History는 계산 근거 보존을 위해 하드 삭제하지 않는다.
- FK는 기본 `RESTRICT`로 유지하고 소프트 삭제된 데이터는 일반 조회에서 제외한다.

## 스케줄·계산 기준 컬럼

- Installment는 `purchase_date`, `first_payment_date`, `next_payment_date`로 월별 일정을 계산한다.
- Loan은 `original_principal`, `repayment_day`, `next_repayment_date`로 상환일정과 예상 이자를 계산한다.
- DepositSaving은 Account의 계좌번호·기관·잔액·상태를 공유하고, `monthly_amount`, `payment_day`, `next_payment_date`로 적금 납입 예정과 부담률을 계산한다.
- 정기예금의 출금계좌는 없을 수 있지만 적금의 출금계좌는 필수이며 입출금계좌만 연결한다.
- 총자산 계산에서는 `DEMAND_DEPOSIT`, `DEPOSIT`, `SAVINGS` 잔액만 합산하고 `MINUS`는 부채로 집계한다.
- `MINUS`의 `account.balance`와 `minus_account.used_amount`는 같은 트랜잭션에서 `balance = -used_amount`가 되도록 갱신한다.
- 모으기 목표의 `current_amount`는 연결 계좌별 `contribution_amount`가 있으면 해당 금액, 없으면 Account 잔액을 합산한 캐시값으로 관리한다.
- 목표를 소프트 삭제하거나 계좌 연결을 변경할 때 GoalAccount 행은 같은 트랜잭션에서 제거·교체하고 GoalHistory는 보존한다.
- `account.last_transaction_date`는 금융 데이터 동기화 시 최신 Transaction 날짜와 함께 갱신한다.
- `available_amount`처럼 파생값을 저장하는 경우 원천값과 같은 트랜잭션에서 갱신하고 CHECK 제약을 만족해야 한다.


# 군집 기반 보조 탐지 확장 (신규 엔티티 없음)

소비 유형 군집 기반 보조 탐지를 위해 **신규 테이블을 추가하지 않고** 기존 `PatternAnalysis`, `DiagnosisIssue`에 nullable 컬럼만 추가한다. 위의 엔티티 연결관계는 변경하지 않는다.

## PatternAnalysis 추가 컬럼

| 컬럼 | 타입 | Null | 설명 |
| --- | --- | --- | --- |
| `model_version` | VARCHAR(50) | Y | 군집 모델 버전 (예: `spending-kmeans-v1`) |
| `cluster_id` | INT | Y | 분류된 군집 번호 |
| `cluster_label` | VARCHAR(50) | Y | 운영자가 부여한 군집 라벨 (예: 변동소비 집중형) |
| `feature_window_months` | INT | Y | 특징 산출 기간(3~6개월) |
| `feature_summary_json` | JSON | Y | 사용자 특징 벡터 요약 (소비율, 저축률, 카테고리 비중 등) |
| `cluster_stats_json` | JSON | Y | 군집별 특징 기준 범위 (min/max, p5/p95) |
| `sample_size` | INT | Y | 군집 표본 수 |
| `confidence` | DECIMAL(5,4) | Y | 분류 신뢰도(중심점 거리 기반) |

## DiagnosisIssue 추가 컬럼

| 컬럼 | 타입 | Null | 설명 |
| --- | --- | --- | --- |
| `detection_source` | VARCHAR(20) | N (기본 `RULE`) | `RULE` / `CLUSTER` / `RULE_AND_CLUSTER` |
| `model_version` | VARCHAR(50) | Y | 근거로 사용한 군집 모델 버전 |
| `cluster_context_json` | JSON | Y | 군집 근거 (`feature`, `rangeMin`, `rangeMax`, `userValue`, `sampleSize`) |

## 적용 기준

- 군집 결과가 없어도 진단이 동작해야 하므로 `detection_source`를 제외한 모든 컬럼은 nullable로 둔다.
- 군집 표본 수·신뢰도 조건을 충족하지 못하면 컬럼을 채우지 않고 `detection_source = RULE`로 저장한다.
- JSON 컬럼은 1차 검증용이며, 제품 기능으로 고정된 필드가 확인된 후에만 정규화 테이블 분리를 검토한다.
- 타 사용자 식별정보나 거래 원문은 저장하지 않고 집계 통계값만 저장한다.

# 2026-09-07 전체 검증 결과

- 기획안, API 명세 1~22, 개발계획과 Jira Day 1~9 완료 기준을 기준으로 엔티티·관계·필수 계산 필드를 재검토했다.
- Dashboard와 AI Coach는 기존 도메인의 계산 결과를 조합하는 서비스이므로 전용 저장 테이블을 추가하지 않았다.
- 외부 연동 응답을 즉시 반환하는 신용등급·상품 조회 항목은 저장 필요성이 확정되지 않아 별도 테이블을 추가하지 않았다.
- 소유권, 민감 식별자, 계산 일정, 이벤트 멱등성, 소프트 삭제, 군집 근거, 다중 목표 영향을 Import DDL에 반영했다.
- 모든 FK 대상 테이블을 참조 테이블보다 먼저 선언하여 ERDCloud가 별도 `ALTER TABLE` 없이 관계를 가져올 수 있게 구성했다.
- 기존 금융상품 SQL의 상태값과 컬럼 계약을 Import DDL에 맞춰 검증했다.
- API CSV에는 상세 응답 스키마가 없으므로 응답 DTO 단위의 완전성은 각 API 구현 전에 별도로 검증한다.
- Import DDL은 신규 스키마 검토용이다. 기존 개발 DB 반영 시에는 데이터 중복과 NULL 값을 먼저 정리한 뒤 별도 Flyway Migration을 작성한다.
