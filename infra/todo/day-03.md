# Day 3 — Nginx 리버스 프록시 정식화 & 도메인/SSL (P0/P1)

Day 2에서 Jenkins 접근용으로 만든 최소 Nginx 설정을 정식 구성으로 확장한다. 외부에서 들어오는 트래픽의 단일 진입점을 Nginx로 만들고, 관리용 도구는 서브패스+인증으로 숨긴다 (포트를 추가로 열 수 없다는 전제 때문).

## 체크리스트

### 1. 도메인/SSL 여부 분기 (🔲 확인 필요)
- [ ] 팀에서 도메인을 구매/할당했는지 확인 (**사용자 액션 필요**: 없으면 이번 주 안에는 IP+포트로 진행하고, 발표 전에만 도메인 연결)
- [ ] 도메인 있음 → A 레코드로 EC2 IP 연결, Let's Encrypt(Certbot) 발급 준비
- [ ] 도메인 없음 → HTTP(IP)로 우선 진행, "SSL/도메인 연결"을 Day 8 통합 리허설 전으로 재일정

### 2. Nginx 설정 확장
- [ ] Day 2의 `/jenkins/` 서브패스 설정을 정리하고 `auth_basic`(htpasswd)로 최소 보호 추가 (지금까지는 급하게 열어둔 상태였을 수 있음)
- [ ] `/api/` → 백엔드(Spring Boot, 아직 더미) 컨테이너로 프록시 규칙 추가 (Day 5에서 실제 백엔드로 교체될 때 그대로 재사용)
- [ ] Day 6에서 붙일 `/grafana/` 서브패스 자리도 미리 예약(설정 스켈레톤만)
- [ ] docker-compose에서 80/443만 호스트에 바인딩되어 있는지 재확인, 나머지 서비스는 내부 네트워크로만 통신하는지 점검

### 3. SSL (도메인이 있는 경우)
- [ ] Certbot 컨테이너 or standalone으로 인증서 발급
- [ ] 인증서 자동 갱신 cron/컨테이너 등록 (`certbot renew` 주기 실행)
- [ ] HTTP → HTTPS 리다이렉트 설정

### 4. 검증
- [ ] 로컬 PC 브라우저/`curl`로 `http(s)://<도메인 or IP>/api/health`(더미 응답) 접근 확인
- [ ] `/jenkins/`가 인증 없이는 401 뜨는지 확인
- [ ] Day 2에서 만든 CI/CD 파이프라인이 Nginx 설정 변경 이후에도 여전히 정상 동작하는지(웹훅 재확인)

## 산출물
- Nginx가 80/443을 물고 있고, `/api/`, `/jenkins/` 라우팅이 정식화됨
- SSL 여부에 대한 결정과 근거가 `00-overview.md`에 반영됨

## 리스크
- 보안그룹을 못 바꾸는 상황에서 443이 애초에 안 열려 있으면 HTTPS 자체가 막힘 → 이 경우 조교에게 443 개방 요청 (**사용자 액션**), 안 되면 HTTP로 발표까지 갈 수도 있음을 팀에 미리 공유
