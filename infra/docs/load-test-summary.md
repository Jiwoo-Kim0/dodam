## 3. 병목은 서버 CPU다 — 근거 4가지

**① 순서:** CPU가 먼저 포화되고 **50초 뒤에** DB 대기가 생겼다.

```
CPU 97% 도달 → (50초 후) → DB 커넥션 대기 발생
```

**② DB는 한가했다.** 커넥션 대기가 100건을 넘는 순간에도
MySQL이 실제로 실행 중인 쿼리는 **2~7개**였다(상한 151). 슬로우 쿼리 0건.
→ 커넥션이 부족한 게 아니라, **커넥션을 쥔 스레드가 CPU를 못 얻어** 반납이 늦은 것이다.

**③ 부하를 2배로 올려도 처리량이 안 늘었다.** 전형적인 포화 곡선이다.

```
60 VU  → 781 req/s        120 VU → 747 req/s  (오히려 감소)
```

**④ 프로파일러(JFR) 결과:** CPU 샘플 18,200개 중
**우리가 작성한 코드는 0.4%**뿐이었다. 나머지는 프레임워크(DB 드라이버·JPA·JSON·모니터링)다.
→ **비즈니스 로직을 고쳐서 얻을 것이 거의 없다.**

**병목이 아닌 것으로 확인된 항목:** 톰캣 스레드(120/200), DB 커넥션 풀,
디스크 I/O(데이터 전부 메모리), JVM 메모리(178MB/1,024MB), 네트워크

| ① | **DB 커넥션의 쿼리 문장 캐시 활성화** | 프로파일에서 DB 드라이버의 **SQL 문장 재해석이 CPU의 10.2%** |
| ② | **사용하지 않는 보안 필터 계측 비활성화** | 모니터링 라이브러리 5.6% 중 **46.5%가 이 계측** |

## 5. 데이터가 4배로 늘어도 성능은 유지됐다

거래 데이터를 6개월 → **24개월(4배, 139만 행)**로 늘린 뒤 다시 측정했다.

| | 6개월 | 24개월 |
| --- | --- | --- |
| 처리량 | 690 req/s | **704 req/s** |
| 지연 p95 | 266ms | **271ms** |

**차이가 측정 오차 수준(±2%)이다.** 조회 API들이 사전 계산된 요약 데이터를 읽기 때문에
원본 거래가 늘어도 비용이 늘지 않는다.

### 거래 목록·집계 API도 별도로 측정했다 (2026-09-25 추가)

원본 거래를 직접 읽는 경로(가계부 화면·일일 브리핑·카테고리별 집계)를
프런트엔드의 실제 호출 패턴 그대로 재현해 측정했다.

| 지표 | 값 |
| --- | --- |
| 처리량 | **852 req/s** (기존 시나리오보다 높음) |
| 오류율 | **0.00%** (20만 요청 · 62만 검증 전건 통과) |
| 지연 p95 | 327ms (API 9개가 316~343ms로 균등) |

**원본 거래를 읽는 경로도 느려지지 않았다.** 사용자별 조회 인덱스가 있어
전체 139만 행이 아니라 **해당 사용자·기간만** 읽기 때문이다.

> ⚠️ **다만 "데이터가 늘어도 안전하다"로 확대하면 안 된다.**
> 측정 계정이 보유한 거래가 246~608건이다. **한 사용자가 수만 건을 보유하는 상황은
> 그런 계정이 없어 측정하지 못했다**(최대 보유자도 1,833건).
