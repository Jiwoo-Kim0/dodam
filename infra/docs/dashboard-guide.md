## 0. 가장 먼저 — 숫자가 아니라 "모양"을 본다

처음 보면 숫자가 많아서 막막하다. **숫자를 외울 필요는 없다.**
그래프가 **평평한가 / 올라가는가 / 튀는가**만 봐도 절반은 읽힌다.

| 모양 | 뜻 |
| --- | --- |
| 평평하다 | 부하를 감당하고 있다 |
| **계단처럼 한 단 올라가고 평평** | **그 지점이 한계다.** 더 밀어도 안 올라간다 |
| 계속 우상향 | 쌓이고 있다. 곧 터진다 |
| 톱니처럼 튄다 | 주기적으로 뭔가 막힌다 (GC, 배치 작업 등) |

**비교 대상이 있어야 "이상한지" 알 수 있다.** 평소 값(무부하)은 이렇다.

```
DB풀 대기 0 · 5xx 0% · p95 0.04초 · CPU 4.8% · 메모리 여유 72%
heap 사용 77MB (확보 248MB / 상한 990MB)
```

## 1. 화면 구성 — 위에서 아래로 좁혀 간다

```
1행  판정   ← "지금 정상인가?" 5초 안에 판단
2행  응답   ← "얼마나 느린가? 어디가 느린가?"
3행  DB     ← "DB가 원인인가?"
4행  자원   ← "서버 자체가 부족한가?"
```

**위에서 아래로 내려가면서 범위를 좁히는 구조다.** 1행이 전부 초록이면 아래를 볼 필요가 없다.

---

## 2. 1행 — 5초 안에 판단하는 칸

### 수집 대상 정상
5개(backend·mysql·redis·node·prometheus)가 모두 살아 있으면 **1(초록)**.

> **0(빨강)이면 다른 패널을 믿으면 안 된다.** 지표가 안 들어오는데 그래프가 평평하면
> "괜찮다"가 아니라 "안 보인다"는 뜻이다. 실제로 2026-09-22까지 backend가 이 상태였다.

### DB풀 대기 ← **가장 중요한 칸**
DB 연결을 못 받고 **줄 서 있는 요청 수**다. 평소 0.

| 값 | 뜻 |
| --- | --- |
| 0 | 여유 있다 |
| 1~4 (노랑) | 슬슬 몰린다 |
| **5 이상 (빨강)** | **커넥션 풀이 가장 좁은 곳이다** |

식당으로 치면 **주방 화구가 다 차서 대기 중인 주문 수**다. 현재 화구는 10개뿐이다.

### 5xx 오류율
서버가 실패한 비율. 평소 0%.

> **1%를 넘으면 부하를 멈춘다.** 더 밀어도 쓸 수 없는 데이터만 쌓인다.
> 참고: 429(너무 많은 요청)는 4xx라 **여기 안 잡힌다.** nginx가 막은 요청은 보이지 않는다.

### 지연 p95
**느린 쪽 5%의 응답 시간.** 평소 0.04초.

평균이 아니라 p95를 보는 이유: 100명 중 95명이 0.1초, 5명이 10초면 **평균은 0.6초**라 괜찮아
보이지만 5명은 10초를 기다렸다. 평균은 느린 소수를 가린다.

### 처리량(req/s)
초당 처리한 요청 수. **부하를 올렸는데 이 값이 안 올라가면 그 지점이 한계다.**

## 3. 2행 — 얼마나, 어디가 느린가

### 지연 분위수 (p50 / p95 / p99)
- **p50**: 절반이 이 시간 안에 끝난다 (보통의 체감)
- **p95 / p99**: 느린 쪽. 사용자 불만은 여기서 나온다

| 모양 | 뜻 |
| --- | --- |
| 셋 다 평평 | 건강 |
| p50은 그대로인데 **p99만 치솟음** | 대부분 괜찮은데 **일부가 막힌다** (락 대기, GC, 커넥션 대기) |
| 셋 다 같이 상승 | 전체가 느려졌다 (자원 포화) |

### 느린 엔드포인트 p95 (상위 7)
**어느 API가 느린지**를 경로별로 보여준다. 개선 대상을 고르는 근거다.

> 하나만 튀면 그 기능의 쿼리를 본다.
> 전부 같이 오르면 특정 기능 문제가 아니라 **공용 자원**(DB풀·CPU) 문제다.

---

## 4. 3행 — DB가 원인인가

### HikariCP 커넥션 풀 ← **여기서 원인이 갈린다**

네 선을 함께 본다.

| 선 | 뜻 |
| --- | --- |
| max(상한) | 쓸 수 있는 최대. 지금 **10** (기본값) |
| active | 지금 쓰는 중 |
| idle | 놀고 있는 것 |
| **pending** | **못 받고 기다리는 요청 수** |

**읽는 법**

- `active`가 10(=max)에 붙고 `pending`이 오른다 → **풀이 좁다.** 화구를 늘려야 한다
- `active`가 10에 한참 못 미치는데 느리다 → **풀 문제가 아니다.** 쿼리·인덱스를 본다

> 참고: MySQL은 151개 연결을 받을 수 있는데 **앱은 10개만 쓴다.**
> DB에 여유가 있어도 앱 쪽에서 먼저 막히는 구조다.

### MySQL 서버
앱 풀이 멀쩡한데 느릴 때 본다.

| 선 | 이상 신호 |
| --- | --- |
| 슬로우 쿼리/초 | 0에서 오르면 **느린 쿼리가 실제로 돌고 있다** |
| InnoDB 락 대기/초 | 오르면 **같은 행을 동시에 고치려고 서로 기다린다** |
| 연결 수 | max_connections(151)에 가까워지면 DB 쪽 한계 |

---

## 5. 4행 — 서버 자체가 부족한가

### JVM 힙과 GC
자바가 쓰는 메모리다. **세 선을 구분해서 본다.**

| 선 | 뜻 | 평소 |
| --- | --- | --- |
| used(사용) | 지금 쓰는 양 | 77MB |
| committed(확보) | JVM이 OS에서 받아둔 양 | 248MB |
| max(상한) | 설정 최대 (`-XX:MaxHeapSize=1g`) | 990MB |

**읽는 법**
- `used`가 `committed`에 붙으면 → JVM이 힙을 늘린다(정상 동작)
- `committed`가 `max`까지 닿은 뒤에도 `used`가 높고 **GC 정지가 함께 오르면** → **메모리 부족**

> **비율(%)로 보지 않는 이유**: GC가 세대 크기를 런타임에 조정해서 max 합계가 변한다.
> 분모가 움직이면 실제 사용량이 늘어도 %가 내려갈 수 있다(2026-09-23에 실제로 겪었다).

**GC 정지**는 "쓰레기 정리하느라 멈춘 시간"이다. 이게 오르면 **코드가 느려진 게 아니라
메모리 정리에 시간을 쓰는 것**이다.

### 호스트 CPU·메모리
**서버 전체**의 상태다. 앱뿐 아니라 MySQL·Redis·Jenkins·Grafana가 같이 쓴다.

| 신호 | 뜻 |
| --- | --- |
| CPU 80% 이상 지속 | **자원 한계.** 앱을 고쳐도 해결되지 않는다 |
| 메모리 여유 15% 미만 | 위험. 컨테이너가 죽을 수 있다 |

### Redis
| 선 | 이상 신호 |
| --- | --- |
| eviction/초 | **0을 넘으면 캐시가 밀려나는 중.** 메모리가 부족해 오래된 키를 버린다 |
| 사용 메모리 | 상한(512MB)에 가까워지는지 |
| 명령/초 | 캐시가 실제로 쓰이는지 |

## 6. 실전 — "느려졌다"에서 시작하는 진단 순서

```
[1] 1행 "수집 대상 정상"이 1인가?
      아니오 → 지표를 못 믿는다. 먼저 이것부터 고친다
      예 ↓

[2] 5xx 오류율이 1%를 넘었나?
      예 → 부하 중단. 로그부터 본다 (Grafana → 도담 — 로그)
      아니오 ↓

[3] DB풀 대기(pending)가 올랐나?
      예 → 원인은 커넥션 풀. 크기를 올리고 재측정
      아니오 ↓

[4] MySQL 슬로우 쿼리나 락 대기가 올랐나?
      예 → 원인은 쿼리·인덱스. 느린 엔드포인트 패널로 대상을 고른다
      아니오 ↓

[5] 호스트 CPU 80% 이상인가?
      예 → 서버 자원 한계. 앱 수정으로 해결 안 됨 (잔여 한계로 기록)
      아니오 ↓

[6] GC 정지가 올랐나?
      예 → 힙 부족. committed가 max에 닿았는지 확인
      아니오 → 처리량이 안 오르면 부하 도구 쪽 한계일 수 있다
```

**한 번에 하나씩만 고치고 다시 잰다.** 여러 개를 동시에 고치면 무엇이 효과였는지 모른다.

## 7. 흔한 오해

| 오해 | 실제 |
| --- | --- |
| "그래프가 평평하니 괜찮다" | 지표가 **안 들어오는 것**일 수 있다. 1행 "수집 대상 정상"을 먼저 본다 |
| "오류율 0%니 문제없다" | 429는 4xx라 안 잡힌다. **nginx가 막은 요청은 보이지 않는다** |
| "평균 응답이 빠르다" | 평균은 느린 소수를 가린다. p95·p99를 본다 |
| "풀을 크게 올리면 빨라진다" | DB도 한계가 있다. 너무 키우면 DB가 더 느려진다 |
| "CPU가 낮으니 여유 있다" | 커넥션 풀 대기 중이면 **CPU는 놀고 응답만 느리다** |

## 8. 대시보드와 스냅샷은 용도가 다르다

| | 용도 | 시간 구간 |
| --- | --- | --- |
| **대시보드** | 부하 중 **실시간 관찰** | `1m` (변화를 빨리 보려고) |
| **`metrics-snapshot.py`** | **전후 비교 기록** | `5m` (흔들림을 줄이려고) |

**보고서에 쓸 수치는 반드시 스냅샷 스크립트로 뜬다.**
구간이 다른 값을 섞어 비교하면 안 된다.

```bash
# 서버에서
python3 /home/ubuntu/app/infra/scripts/metrics-snapshot.py
```

결과는 배포 커밋과 함께 `load-test-records.md`에 이어 적는다.
**어떤 코드에서 난 수치인지 없으면 비교가 성립하지 않는다.**
