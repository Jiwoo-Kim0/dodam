# 서비스는 부하를 어떻게 견디나 — 입문용 정리

작성일: 2026-09-22. 부하 테스트(S15P21D105-693)를 준비하며 정리했다.
용어를 모르는 사람도 읽을 수 있게 썼고, 설명마다 **이 프로젝트의 실제 숫자**를 붙였다.
지표 정의는 [monitoring.md](monitoring.md), 측정 기록은 [load-test-records.md](load-test-records.md).

---

## 0. 부하란 무엇인가

"부하가 걸린다"는 건 **요청이 처리 능력보다 빨리 들어온다**는 뜻이다.
그러면 어딘가에서 **줄이 생긴다.** 줄이 길어지면 응답이 느려지고, 더 길어지면 실패한다.

식당에 비유하면 이해가 쉽다.

| 식당 | 서버 |
| --- | --- |
| 손님 | 요청(request) |
| 주문 받는 직원 | 웹 서버 스레드 (Tomcat, 기본 200개) |
| 주방 화구 | **DB 커넥션 풀** (HikariCP, 기본 **10개**) |
| 재료 창고 | 데이터베이스 (MySQL) |
| 미리 만들어 둔 반찬 | 캐시 (Redis) |
| 주문이 오래 걸리는 외부 업체 | 외부 API (OpenAI 등) |

**직원이 200명이어도 화구가 10개면 동시에 10개 요리만 된다.**
나머지 190명은 주문만 받아놓고 기다린다. 이게 이 프로젝트의 현재 구조다.

---

## 1. 제일 먼저 알아야 할 것 — 병목

> **전체 속도는 가장 좁은 곳이 정한다.**

직원을 400명으로 늘려도 화구가 10개면 소용없다. 오히려 주방 앞에 사람만 더 쌓인다.

그래서 성능 개선은 **"어디가 제일 좁은지 찾는 것"**부터 시작한다.
찾지 않고 이것저것 고치면, 고쳤는데 아무 변화가 없는 일이 생긴다.

부하 테스트의 목적이 바로 이 **가장 좁은 곳을 찾는 것**이다.

## 2. 상용 서비스가 쓰는 방법들

### 2-1. 용량을 기본값에 맡기지 않는다

프레임워크 기본값은 "아무 서비스에나 무난한 값"이지 **우리 서비스에 맞는 값이 아니다.**

이 프로젝트의 현재 값:

```
웹 서버 스레드   : 200   (기본값)
DB 커넥션 풀     :  10   (기본값)   ← 가장 좁은 곳
MySQL이 받을 수 있는 연결 : 151
```

DB는 151개까지 받을 수 있는데 **앱은 10개만 쓰고 있다.**

**중요한 오해**: "그럼 100으로 올리면 10배 빨라지나?" → **아니다.**
DB도 동시에 처리할 수 있는 양이 정해져 있어서, 너무 크게 잡으면 DB가 더 느려진다.
적정값은 보통 `(CPU 코어 수 × 2)` 언저리에서 시작해 **측정해서 정한다.**

### 2-2. 느린 것 하나가 전체를 멈추지 않게 한다

외부 업체에 주문을 넣었는데 답이 없다고 하자. 직원이 계속 기다리면 **그 직원은 다른 손님을 못 받는다.**
이런 직원이 200명 다 묶이면 식당 전체가 멈춘다.

그래서 상용에서는 세 가지를 건다.

1. **타임아웃** — "N초 기다리고 안 오면 포기"
2. **폴백(대체 동작)** — 포기했을 때 **대신 보여줄 것**
3. **차단기** — 계속 실패하면 아예 시도를 멈췄다가 나중에 다시 해본다

> **이 프로젝트가 이미 잘 하고 있는 부분이다.**
> AI 코치는 연결 3초·응답 12초 타임아웃을 걸고, 실패하면 서버가 만든 템플릿 문장으로 대체한다.
> 그래서 OpenAI가 죽어도 화면은 정상으로 보인다. (`backend/docs/ai-coach.md` §7)

### 2-3. 같은 걸 또 만들지 않는다 — 캐시

주문마다 재료 창고에 다녀오는 대신, **자주 나가는 반찬은 미리 만들어 둔다.**
이게 캐시(Redis)다.

캐시가 잘 맞는 데이터는 이렇다.
- **자주 읽고** (많이 조회되고)
- **드물게 바뀌고** (금방 낡지 않고)
- **조금 낡아도 괜찮은** 것

이 프로젝트는 Redis를 띄워 뒀지만 **AI 코치 응답 캐시 한 곳에서만** 쓴다.
부하 테스트에서 느린 조회가 나오면, 쿼리를 고치기 전에 **"이건 캐시해도 되나"를 먼저 보는 쪽이 대개 더 싸다.**

### 2-4. 데이터를 빨리 찾게 한다 — 쿼리와 인덱스

창고에서 재료를 찾는 데 오래 걸리면 화구가 비어도 요리가 안 나온다.

**인덱스**는 책 뒤의 "찾아보기"와 같다. 없으면 1페이지부터 넘겨가며 찾는다(풀 스캔).
데이터가 100건일 때는 차이가 없지만 100만 건이면 결정적이다.

이 프로젝트는 느린 쿼리를 자동으로 기록하게 해 뒀다(1초 이상, `slow.log`).

### 2-5. 안 기다려도 되는 일은 나중에 한다 — 비동기

주문한 손님이 **꼭 그 자리에서 기다려야 하는 일**이 아니면, 접수만 하고 나중에 처리한다.
영수증 이메일 발송 같은 것이 그렇다.

반대로 "진단 결과를 보여줘" 같은 건 **기다리는 게 맞다.** 무조건 비동기가 좋은 게 아니다.

### 2-6. 가게를 늘린다 — 수평 확장

가장 근본적인 방법이다. 같은 앱을 **여러 대** 띄우고 앞에서 나눠준다(로드 밸런서).

다만 그러려면 앱이 **어느 대에서 처리하든 결과가 같아야** 한다.
특정 서버 메모리에만 뭔가 저장해 두면 다음 요청이 다른 서버로 갔을 때 깨진다.

> **이 프로젝트에서는 지금 어렵다.** 5절 참고.

### 2-7. 못 받으면 빨리 거절한다 — 부하 차단

손님이 넘치는데 계속 받으면 **모두가 30분씩 기다리다 화를 낸다.**
차라리 "지금은 자리가 없습니다"라고 **빨리 말하는 편이 낫다.**

상용은 한계를 넘으면 기다리게 하지 않고 즉시 **503**을 돌려준다.
지금 이 프로젝트에는 이 장치가 없어서, 부하가 걸리면 **응답 시간이 계속 늘어난다.**

### 2-8. 한 사람이 다 쓰지 않게 한다 — 레이트 리밋

한 손님이 100인분을 시키면 다른 손님이 굶는다. 그래서 **1인당 상한**을 둔다.

**기준을 무엇으로 잡느냐가 중요하다.**

| 기준 | 언제 쓰나 | 문제 |
| --- | --- | --- |
| **IP 주소** | 로그인 전(아직 누군지 모름) | 같은 와이파이·통신사를 쓰면 **여러 명이 한 사람으로 취급**된다 |
| **사용자 ID** | 로그인 후 | 정확하다. 토큰이 있으면 이쪽을 쓴다 |

이 프로젝트의 현재 상태:
- nginx: **IP당 초당 20요청** (로그인은 분당 20)
- AI 코치: **사용자당 시간당 40회** ← 올바른 형태

코치 쪽이 교과서적으로 맞다. 외부 과금이 걸린 기능을 **사용자 단위**로 제한한다.
반면 nginx는 로그인 후 요청까지 IP로 재고 있어, 캠퍼스 와이파이처럼 **IP를 공유하면 서로 방해**한다.

## 4. 측정하지 않고 고치지 마라

초보자가 가장 많이 하는 실수는 **추측으로 고치는 것**이다.

> "느린 것 같으니 커넥션 풀을 100으로 올리자"

→ 병목이 쿼리에 있었다면 아무 효과가 없고, DB만 더 힘들어진다.
→ 게다가 **원래 뭐가 문제였는지 영영 알 수 없게 된다.**

올바른 순서는 이렇다.

1. **재본다** (부하 전 수치 기록)
2. **부하를 걸고 어디가 막히는지 본다**
3. **한 가지만 고친다**
4. **다시 재서 비교한다**

한 번에 여러 개를 고치면 **무엇이 효과가 있었는지 모른다.**

### 이 프로젝트의 판단 기준

| 증상 | 원인 |
| --- | --- |
| `DB풀 대기`가 오르고 응답이 느려짐 | **커넥션 풀이 좁다** (쿼리 문제가 아님) |
| `DB풀 대기`는 0인데 느림 | **쿼리·인덱스** 문제 |
| 호스트 CPU가 80% 넘게 지속 | **서버 자원 한계** (앱을 고쳐도 소용없음) |
| Redis eviction이 0을 넘음 | 캐시가 밀려나는 중 |

## 5. 왜 이 프로젝트는 수평 확장이 어려운가

**EC2 한 대에 전부 들어 있다.**

```
EC2 1대 ─ MySQL · Redis · 백엔드 · nginx · Jenkins · Grafana · Prometheus · Loki
```

앱을 2개 띄워도 **같은 CPU와 메모리를 나눠 쓸 뿐**이라 처리량이 늘지 않는다.
오히려 메모리가 부족해질 수 있다.

또 하나, `NotificationEventScheduler`처럼 **정해진 시각에 도는 작업**이 있는데
앱이 2대면 **같은 알림이 두 번 발송된다.** (해결하려면 "한 대만 실행" 장치가 필요하다)

**그래서 지금 할 수 있는 것은 "한 대를 잘 쓰는 것"(세로 개선)이고,
"여러 대로 늘리는 것"(가로 개선)은 자원을 분리한 뒤의 이야기다.**

이건 실패가 아니라 **구조상의 상한**이며, 발표에서는 그렇게 설명하는 편이 정확하다.

## 6. 용어 정리

| 용어 | 뜻 |
| --- | --- |
| **병목** | 전체 속도를 결정하는 가장 좁은 구간 |
| **커넥션 풀** | DB 연결을 미리 만들어 두고 돌려쓰는 묶음. 매번 새로 연결하면 느리다 |
| **스레드** | 요청 하나를 처리하는 일꾼 |
| **캐시** | 자주 쓰는 결과를 빠른 곳에 미리 담아 두는 것 |
| **인덱스** | 데이터를 빨리 찾기 위한 "찾아보기" |
| **타임아웃** | 정해진 시간 안에 응답이 없으면 포기하는 것 |
| **폴백** | 실패했을 때 대신 보여주는 것 |
| **레이트 리밋** | 정해진 시간 동안 허용하는 요청 수 상한 |
| **수평 확장** | 서버 대수를 늘리는 것 |
| **수직 확장** | 서버 한 대의 성능(CPU·메모리)을 키우는 것 |
| **p95 / p99** | 느린 쪽 5% / 1%의 응답 시간. 평균보다 체감에 가깝다 |
| **부하 차단** | 한계를 넘으면 기다리게 하지 않고 즉시 거절하는 것 |

### 왜 평균이 아니라 p95를 보나

100명 중 95명이 0.1초, 5명이 10초 걸렸다고 하자.
**평균은 0.6초**라 괜찮아 보이지만, **5명은 10초를 기다렸다.**

평균은 느린 소수를 가린다. 그래서 상용에서는 p95·p99를 본다.
이 프로젝트도 그래서 히스토그램을 켜 두었다.
