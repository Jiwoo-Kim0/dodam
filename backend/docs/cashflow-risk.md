작성일 2026-09-10. 저장 계층은 [cashflow.md](cashflow.md)(538), 이벤트 수집은
[cashflow-events.md](cashflow-events.md)(539), 실행·계산 로직은
[cashflow-daily-balance.md](cashflow-daily-balance.md)(540), HTTP 계층 공통 계약은
[cashflow-query.md](cashflow-query.md)(541)를 따른다. 이 문서는 그 위에 얹은 **위험 탐지와 오늘
사용가능금액**만 다룬다.

작업 브랜치는 `S15P21D105-542-api-15-risks-available-today`이며 `origin/develop`이 아니라 **541
브랜치 tip에서 분기**했다. 541이 만든 `CashflowQueryService`의 최신 예측 해석과 Repository 조회
메서드를 그대로 쓰기 때문이다. **541이 `develop`에 병합된 뒤에 병합해야 한다.**

Jira 사이트에서 542를 조회하지 못했다. 로컬 `SPRINT/Jira (4).csv`의 제목은 `[API 15] 위험·가용금액`,
설명은 `risks·available-today 구현`, 상위 작업은 `S15P21D105-465`다. **최신 Jira 완료 조건을 대신하지
않는다.**

## 위험 탐지

### 판정 지점

기획안 "공통 현금흐름 예측 로직"과 같이 **출금 직전 잔액**으로 판정한다. 하루 안에서 입금을 먼저,
출금을 나중에 반영한 뒤 각 출금마다 `잔액 < 출금액`이면 부족 1건이다.

하루 마감 잔액으로 판정하지 않는 이유는 두 가지다.

- 같은 날 여러 건이 빠져나갈 때 **어느 출금에서 처음 막히는지** 알 수 없다.
- 한 번 음수가 되면 이후 날짜가 이월된 음수 때문에 전부 위험으로 잡혀 목록이 무의미해진다.

탐지는 `CashflowDailyBalanceCalculator`의 잔액 순회 안에서 함께 이뤄지고(`CashflowShortage`),
유형·심각도·문구를 입히는 정책만 `CashflowRiskDetector`가 맡는다. 별도 클래스가 같은 순회를 다시
돌면 입금·출금 반영 순서가 두 곳에 생겨 한쪽만 바뀔 수 있다.

### `cashflow_risk.type`

ERD 주요 코드값 표에 이 컬럼의 값 목록이 없어 542에서 정한다. **현재 값 집합은 다음 하나다.**

| 값 | 의미 |
| --- | --- |
| `BALANCE_SHORTAGE` | 예정 출금일에 잔액이 모자란다 |

지금 탐지 규칙이 이것 하나뿐이므로 값도 하나다. 없는 유형을 미리 정의하지 않는다. 유형이 늘면
`CashflowRiskDetector`에 상수를 추가하고 ERD 코드값 표를 함께 갱신한다.

`type` 필터는 값 집합을 닫지 않고 `^[A-Z][A-Z0-9_]{0,49}$` 형식만 검증한다(541의 `events`와 같은
이유). 형식이 맞지만 탐지된 적 없는 값은 400이 아니라 **빈 결과**다.

### 심각도

`severity`는 ERD 주요 코드값 표의 `LOW`/`MEDIUM`/`HIGH`/`CRITICAL`을 그대로 쓴다. 판정 기준은 명세에
없어 정한 **서비스 기본안**이다.

| 조건 | 심각도 |
| --- | --- |
| 출금 직전 잔액 ≤ 0 | `CRITICAL` |
| 부족액 / 필요금액 ≥ 0.5 | `HIGH` |
| 부족액 / 필요금액 ≥ 0.2 | `MEDIUM` |
| 그 외 | `LOW` |

절대금액이 아니라 **비율**을 쓴다. 같은 10만원 부족도 소득 규모에 따라 의미가 달라 금액 임계값은
사용자마다 다시 정해야 하지만, "필요한 돈의 몇 %가 비었나"는 사용자와 무관하게 해석이 같다. 잔액이
이미 음수면 비율이 100%를 넘어 구간이 무의미해지므로 먼저 `CRITICAL`로 거른다.

**임박도(기준일로부터 며칠 뒤인지)는 반영하지 않는다.** 오늘 부족과 89일 뒤 부족의 긴급도는 분명히
다르지만, 가중치가 또 하나의 임의값이 된다. 날짜는 `riskDate`로 그대로 제공하며 호출자가 판단한다.

### 정렬

**심각도 내림차순 → `riskDate` 오름차순(NULL은 뒤) → `riskId` 오름차순.**

DB가 아니라 메모리에서 정렬한다. `severity`가 문자열 컬럼이라 SQL 사전순(`CRITICAL` < `HIGH` < `LOW`
< `MEDIUM`)이 심각도순과 다르기 때문이다. enum 선언 순서를 쓰면 정렬 기준이 코드값 정의 한 곳에만
남는다. 538이 542로 미뤄 둔 결정이다.

위험 행은 예측 1건당 예정 출금 건수를 넘지 않아(대부분 수십 건) 메모리 정렬과 페이지 미분할이
문제되지 않는다. 명세에도 페이지 파라미터가 없다.

### 문구

`message`는 `"<이벤트명> <필요금액>원 출금 예정이나 <부족액>원이 부족합니다."` 형식이다.

- 계좌번호·카드번호는 담지 않는다. 이 문구는 응답과 DB에 그대로 남아 회수할 수 없다.
- `cashflow_risk.message`가 VARCHAR(500)이라 이벤트명을 100자로 잘라 상한을 넘지 않게 한다.

### `expected_balance`와 `forecast.risk_date`

- 위험 행의 `expectedBalance`는 **그 출금 직전** 잔액이다. 하루 마감 잔액이 아니므로
  `daily-balances`의 같은 날짜 값과 다를 수 있다.
- `cashflow_forecast.risk_date`는 540이 구한 "잔액이 처음 음수가 되는 날"을 그대로 쓴다. 첫 부족
  사건의 날짜와 **언제나 같다**. 잔액은 출금으로만 줄고, 0 이상에서 음수로 넘어가는 출금은 정의상
  `잔액 < 출금액`이라 반드시 부족으로 잡히기 때문이다.

## 오늘 사용가능금액

### 계산 정의

```
available_today = max(0, 예측 구간 최소 예상잔액)
```

명세에 계산식이 없어 정한 **서비스 기본안**이다. "앞으로 확정된 출금을 모두 감당하고도 오늘 꺼내 쓸
수 있는 금액"이라는 뜻이다. 오늘 마감 잔액만 쓰면 내일 카드대금이 빠져나가도 오늘은 여유가 있는
것처럼 보인다.

`min(오늘 마감 잔액, 구간 최소 잔액)`으로 쓸 필요는 없다. 최소 잔액은 기준일 마감 잔액을 포함해 고른
값이라 둘의 최소값과 항상 같다.

음수는 **0으로 막는다.** "사용가능금액 -30만원"은 쓸 수 있는 돈의 크기가 아니다. 부족 사실은 위험
행과 `minimumBalance`가 따로 전달한다.

기획안 685행의 "가용금액"(소득 − 고정지출 − 저축)은 **월 단위 진단 개념**이며 이 값과 다르다. 서로
대체하지 않는다.

### 저장과 조회

`available_today`는 예측 실행 시점에 계산해 컬럼에 저장하고, 조회는 저장값을 그대로 읽는다. 조회
시점에 다시 계산하면 같은 예측을 두 번 조회했을 때 값이 달라질 수 있고 `daily-balances`와도 어긋난다.

**542 이전에 완료된 예측에는 값이 없어 `null`이다.** 0원으로 채우지 않는다. "쓸 돈이 없다"와 "계산된
적이 없다"는 다르다. 예측을 다시 실행하면 채워진다.

## 입력과 오류

| 입력 | 대상 | 검증 |
| --- | --- | --- |
| `type` | `/risks` | `^[A-Z][A-Z0-9_]{0,49}$`. 위반 시 `VALIDATION_ERROR`(400). 형식이 맞고 없는 값은 빈 결과 |
| `severity` | `/risks` | `RiskSeverity` enum. 잘못된 값은 `INVALID_REQUEST`(400) |
| `baseDate` | `/available-today` | ISO 날짜. 지정하면 그 기준일의 최신 완료 예측, 없으면 마지막에 완료된 예측 |

`severity`가 `VALIDATION_ERROR`가 아닌 이유는 enum 변환이 필드 단위 오류를 만들지 못하고 전역
처리기의 `MethodArgumentTypeMismatchException` 경로로 가기 때문이다. 날짜 형식 오류와 같은 계약이다.
임의의 응답 형식을 추가하지 않았다.

## 응답 계약

### GET /risks

```json
{
  "success": true,
  "data": {
    "forecast": { "forecastId": 1, "baseDate": "2026-09-10", "availableToday": 0, "minimumBalance": -300000, "riskDate": "2026-09-11", "...": "..." },
    "type": null,
    "severity": null,
    "risks": [
      { "riskId": 2, "riskDate": "2026-09-12", "type": "BALANCE_SHORTAGE", "severity": "CRITICAL", "message": "적금 납입 100,000원 출금 예정이나 300,000원이 부족합니다.", "expectedBalance": -200000 }
    ]
  }
}
```

적용한 필터를 되돌려 준다. 빈 목록이 "위험이 없다"인지 "필터에 걸린 게 없다"인지 구분하기 위해서다.
예측 헤더를 함께 싣는 것은 `daily-balances`·`events`와 같은 이유다.

### GET /available-today

```json
{
  "success": true,
  "data": {
    "forecast": { "forecastId": 1, "availableToday": 500000, "...": "..." },
    "availableToday": 500000
  }
}
```

`availableToday`는 예측 헤더에도 있지만 최상위에 한 번 더 싣는다. 이 엔드포인트의 결과가 그 값
하나이므로 호출자가 헤더 안을 파고들지 않게 한다.

### 541 응답의 변경

`CashflowForecastResponse`에 **`availableToday` 필드를 추가했다.** 541이 계산 정의 확정 시점에
추가하기로 남겨 둔 항목이다. 기존 필드는 그대로이며 순서만 `currentBalance` 다음이다.

## 검증

`.\gradlew.bat test` 전체 통과(H2). 542가 추가한 테스트는 다음과 같다.

- `CashflowRiskDetectorTest`: 정상(위험 없음), 부족 탐지 지점, 같은 날 입금 우선, 하루 여러 출금 중
  실제로 막히는 건만 탐지, 심각도 4구간 경계값, 이미 음수인 잔액, 가용금액의 구간 최소값 사용과 0 절삭
- `CashflowApiIntegrationTest`: 두 엔드포인트의 정상 응답, 심각도 우선 정렬, `type`·`severity` 필터,
  없는 유형의 빈 결과, 인증 실패(401), 타인 예측 격리(404), 잘못된 `type`·`severity`(400)
- `CashflowForecastRunnerTest`: 실행 시 위험 행 저장과 `available_today` 채움

**MySQL에서는 검증하지 않았다.** 새 마이그레이션과 스키마 변경이 없어 검증할 DDL 변경은 없지만, H2
통과가 MySQL 제약·타입 검증을 대신하지 않는다. 남은 작업에 기록했다.

## 현재 제한사항

- 탐지 규칙이 `BALANCE_SHORTAGE` 하나다. 적금 납입일 부족 등 기획안의 개별 시나리오도 모두 이 규칙
  하나로 잡히며, 유형으로 구분되지 않는다.
- 마이너스통장 한도 여력을 반영하지 않는다. 한도가 남아 있어 실제로는 결제되는 출금도 부족으로 잡힌다.
  minusaccount 도메인 조회가 필요해 이번 범위에서 제외했다.
- 요일별 평균 변동지출이 반영되지 않아(540) 예상잔액이 낙관적이다. 실제보다 **위험을 적게** 보고한다.
- `AccountScheduledEventSource` 구현체가 없어 급여 등 예정 입금이 반영되지 않는다. 반대로 실제보다
  **위험을 많게** 보고한다. 위 항목과 상쇄 방향이지만 크기는 알 수 없다.
- `available_today`가 예측 구간 전체(기본 90일)의 최소값이라 먼 미래의 큰 출금 한 건이 오늘 값을
  끌어내린다.
