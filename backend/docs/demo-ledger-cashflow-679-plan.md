### 3-8. `saving-ratio` 저축률 정의 통일 (API 변경, 2026-09-21 사용자 결정으로 담당 범위에 포함)

`GET /spending/saving-ratio`의 `savingRatioPercent`는 현재 `remaining / income`(남는 돈 비율, 통계청 흑자율 개념)이다. 같은 리포트 화면의 효율 점수는 `저축성 지출(NON_SPENDING EXPENSE) / 소득`을 쓰므로 U0003에서 49.8%와 28.1%가 나란히 뜬다. 담당이 바뀌어 이 API 정의를 이번에 함께 맞춘다.

- 변경: `savingRatioPercent = savingTransfer / income`. `savingTransfer`는 이미 응답에 있는 NON_SPENDING 합이라 리포트 `totalSaving`과 같은 정의다. `remaining`은 그대로 두고 `remainingRatioPercent`(= 기존 값)를 추가해 정보를 잃지 않는다. `targetSavingRatioPercent`(100 − 목표 소비 비율)는 소비목표 개념이라 손대지 않고 Javadoc에 차이를 적는다.
- 영향: FE `useReportData`는 필드명이 같아 수정이 없고 `≥ 20% → good` 판정도 유효하다(U0003 28.1%). 홈·가계부는 이 필드를 쓰지 않는다. 시뮬레이션·코치 facts가 이 API를 읽는지 구현 시 grep으로 확인한다.
- 산출물: `SpendingAnalysisService`·`SavingRatioResponse`·관련 테스트(정의 변경·`remainingRatioPercent`·소득 0·NON_SPENDING 0)·[spending-aggregation.md](spending-aggregation.md) 507 절. 루트 `docs/` API 명세 6의 설명 갱신은 사용자에게 알리고 요청 시 반영한다.
- MR은 seed와 분리한다(API 계약 변경 vs 시연 데이터). 브랜치·Jira 번호는 사용자 지정에 따른다.

## 6. 미지원 기능 — BE(스프린트 214/213, 구동재) 인계 항목

DB seed로 해결할 수 없어 이번 범위에서 제외하고 사실만 기록한다.

1. **급여·고정지출 예정 이벤트 없음**: `AccountScheduledEventSource` 구현체가 없어 예측에 `ACCOUNT_INCOME`·`ACCOUNT_EXPENSE`가 없다. `financial_profile.payday·monthly_income`과 원장의 FIXED 반복 거래로 다음 회차를 추정하는 어댑터가 필요하다. 이것이 없으면 잔액 부족 위험 시연은 항상 "출금만 있는" 비관적 예측이라 의미가 없다.
2. **예측 자동 실행 없음**: FE·BE 어디서도 `POST /forecasts`를 호출하지 않는다. 홈 진입·금융 연동 완료·진단 실행 시 예측을 만들거나 FE가 404에서 생성 요청을 보내는 흐름이 필요하다. 시연은 4단계의 수동 호출로 대체한다.
3. **변동지출 미반영**: 예측이 요일별 평균 변동지출을 차감하지 않는다(540 제한).
4. **카드 연결 구독 vs 청구서 대사**: 청구서에 구독이 포함된다는 근거 데이터가 없어 항상 `CARD_SUBSCRIPTION_REQUIRES_BILLING_RECONCILIATION` 사유가 남는다.
5. **`incompleteReasons` 미저장**: 조회 API·캐시 응답에서 사유가 보이지 않는다.
6. **진단 규칙 미정의**: `FIXED_SPENDING_INCREASE`·`CARD_PAYMENT_BURDEN`·`SAVING_CASHFLOW_BURDEN` 등은 `RULE_POLICY_NOT_DEFINED`다. 이번 데이터로 고정지출 증가 시나리오를 만들어도 진단에 나타나지 않는다.
7. 카드대금 출금을 원장에 표시하는 계약(TRANSFER/NON_SPENDING 취급, 화면 표기)이 없다(3-5절).

## 7. 남은 위험

- 679 브랜치가 678을 포함하지 않아 MR 순서 의존이 생긴다(678 먼저 병합). README 17번 절과 16번 절의 병합 충돌 가능.
- `saving-ratio` 정의 변경은 다른 화면·코치 facts가 이 값을 읽고 있으면 문구가 바뀐다. 구현 시 호출처를 전수 확인한다.
- U0003 고정비·저축 비율 변경으로 패턴 분석 군집이 바뀔 수 있다. 바뀌면 또래 비교 화면 문구가 달라지므로 QA 보고서에 기록하고 필요 시 금액을 조정한다.
- 카드 청구서 추가는 카드 결제 부담률·할부 가용자금 등 다른 카드 API 기대값을 바꿀 수 있다. 3단계에서 함께 실측한다.
- 리포트 효율 점수·코치/시뮬레이션 facts가 U0003 소비 구조를 읽으므로 기존 시연 대본의 수치(고정지출 비중 79% 등)가 있으면 함께 고쳐야 한다. 315 PPT·대본 작업에 반영한다.
- 시연 서버 적재는 별도 요청·인프라 절차다. 이 계획으로 서버를 바꾸지 않는다.
