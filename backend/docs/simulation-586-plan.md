## 2. 입력과 데이터

아래 범위·기본값·단위는 원본 명세에 없는 서비스 보완안이다. 실제 금융기관 약정이나 법정 상한을 뜻하지 않는다.

| 유형 | 요청 | 검증·기본값 |
| --- | --- | --- |
| 할부 | purchaseAmount, months, feeRate? | 원금 양수 정수, months 1~120, feeRate 생략/null은 0 |
| 리볼빙 | cardId?, balance, paymentRatio, rate | cardId 양수·본인 카드, balance 양수 정수, 0 < paymentRatio ≤ 100, rate 필수 |
| 현금서비스 | amount, rate, repaymentMonths? | amount 양수 정수, rate 필수, repaymentMonths 생략/null은 1, 1~120 |
| 복합 | scenarios[] | 2~10개, 각 원소는 {type, parameters}, type은 COMBINED 제외 9종 |

- 금리·수수료율은 연율 %, 결제비율도 %다(12 = 연 12%, 10 = 10%). BigDecimal 소수 4자리까지, 금리 0~100을 계산 입력 상한으로 사용한다.
- 금액은 long 원 단위다. 신규 DTO의 소수 금액을 묵시적으로 절사하지 않도록 전용 역직렬화/검증을 적용한다. 전역 ObjectMapper 설정은 바꾸지 않는다.
- 날짜는 SimulationClock의 Asia/Seoul 기준일을 실행 중 한 번만 확보한다. 날짜 입력이 없으므로 실제 카드 청구 주기를 추정해서 읽지 않는다.
- cardId는 소유권·대상 식별에만 사용한다. 입력 balance/rate/paymentRatio를 카드 DB 값으로 덮어쓰지 않는다. 카드번호는 입력·로그·저장·응답에 포함하지 않는다.
- 공통 기준선은 기존 Reader의 월소득, 직전 3개 달력월 소비, 활성 목표·연결 계좌를 재사용한다. 누락 시 기존 coverage를 보존한다.
- 리볼빙·현금서비스 약정 테이블이나 외부 데이터 적재는 추가하지 않는다. 계산 조건의 dataSource는 USER_INPUT이고 baseline 출처는 LOCAL_DB로 구분한다.
- 복합에 예적금·대출 유형이 들어가면 585의 상품·대출 스냅샷과 검증을 그대로 사용한다.

Seed는 491·492·493과 카드 522를 재사용할 수 있다. 단독 할부/현금서비스 계산에는 기존 할부 레코드가 필수는 아니다.
시연 계정 로그인 준비는 앱 통합 선행 조건이며 단위·H2 통합 테스트는 자체 fixture로 진행한다.

## 3. 계산 기본안

### 공통

- 기획안의 일할 이자식에 따라 `회차 시작 잔액 × 연율 / 100 × 실제 경과일수 / 365`를 사용한다. 윤년도 분모 365인 ACT/365 추정 모형이다.
- 회차 이자·수수료는 원 단위 HALF_UP, 합계는 확정된 회차 금액 합이다. 원금은 회차별 정수 배분 후 마지막 회차가 잔액을 정산한다.
- 회차일은 `기준일.plusMonths(k)`로 매번 최초 날짜에서 구한다. 1/31 → 2월 말 → 3/31로 복원한다.
- 합·차·누적·BigDecimal→long 변환은 범위 초과를 검출하고 기존 SIMULATION_AMOUNT_OUT_OF_RANGE로 처리한다.
- 신규 계산은 사용자 전체 잔액·지급 능력 판단이 아니라 행동 전후의 현금 변화다. 세금·연체료·추가 이용·금리 변동·기관별 최소결제액은 반영하지 않으며 assumptions에 남긴다.
- 530은 저장된 monthlyAmount 기반의 잔여 일정 조회다. 이를 신규 구매의 수수료 계산기로 재사용하지 않는다. 실제 약정과 서비스 추정의 차이를 응답 details.calculationPolicy로 식별한다.

### 3.1 할부

1. 비교 전: 기준일에 purchaseAmount 전액 결제.
2. 비교 후: 기준일 현금 결제 없음, 다음 달부터 months회 원금 균등 상환과 잔액 기준 수수료 납부.
3. 기본 회차 원금은 floor(purchaseAmount / months), 마지막 회차는 잔액 전액이다. 원금보다 개월 수가 커서 앞 회차 원금이 0인 경우도 명시적으로 허용한다.
4. feeRate 생략/null은 적용률 0·`feeRateMode=ASSUMED_ZERO`로 정규화하고 `ZERO_FEE_ASSUMED`를 남긴다. 명시한 0을 포함한 수수료율 입력은 `feeRateMode=EXPLICIT`이며 이 가정 코드를 붙이지 않는다. 어느 모드도 실제 기관의 무이자 혜택을 확인한 것은 아니다. 적용률과 모드를 요청·scenario 파라미터, 결과 details와 요청 지문에 보존한다. 모드는 서버가 결정하며 클라이언트 입력 필드로 받지 않는다.
5. 현금 delta는 기준일 +purchaseAmount, 각 회차 -(원금+수수료). 전체 delta 합은 -총수수료다.
6. 기준일 부채 변화는 +purchaseAmount, 현금 보존액도 +purchaseAmount다. 같은 구매 물품 가치는 전후 공통이므로 자산에 다시 추가하지 않는다.

### 3.2 리볼빙

1. balance를 **기준일에 결제할 카드대금**으로 해석한다. 비교 전에는 기준일 전액 결제한다.
2. 비교 후 기준일 원금 결제는 `min(balance, max(1, ceil(balance × paymentRatio / 100)))`, 나머지를 이월한다. 최초 결제 전의 과거 이자는 계산하지 않는다.
3. 다음 회차부터 시작 잔액에 ACT/365 이자를 계산한다. 원금 결제는 같은 결제비율 식, 이자는 매회 전액 납부한다. 이자에 다시 이자를 붙이지 않는다.
4. 최대 120개 월 회차까지만 계산한다. 잔액이 남으면 강제 전액 상환으로 조작하지 않고 `paidOff=false`, `remainingBalance`, `evaluatedThrough`, `terminationReason=HORIZON_LIMIT`을 제공한다.
5. 기준일 현금 delta는 balance-최초 결제원금, 이후에는 -(회차 원금+이자)다. 계산 기간 합은 남은 잔액-누적이자로 검산한다. 미상환 잔액을 이익으로 표시하지 않는다.
6. paymentRatio=100이면 기준일 전액 결제, 이자 0, 이후 일정 없음이다.
7. 금융기관의 실제 약정결제비율 계산과 최소청구액을 재현하지 않는 `PRINCIPAL_RATIO_WITH_INTEREST_PAID_SEPARATELY` 모형임을 명시한다.

### 3.3 현금서비스

1. 비교 전은 신규 이용 없음이다. 비교 후 기준일 amount 유입과 같은 금액의 부채 증가를 반영한다.
2. repaymentMonths개월 후 만기에 원금을 일시 상환하고, 기준일~만기 ACT/365 단리 이자를 함께 납부한다. 중간 월 납부는 없다.
3. 기본 1개월과 1개월 초과 모두 사용자 지정 상환기간의 추정 시나리오이며 실제 기관에서 해당 기간의 약정을 제공한다는 뜻은 아니다.
4. 전체 현금 delta 합은 -이자, 원금 유입 시 순자산 변화는 0이다.

## 4. 복합 시나리오 계약

### 요청 구조와 순환 금지

```json
{
  "scenarios": [
    { "type": "SPENDING", "parameters": { "monthlyReduction": 50000, "durationMonths": 12 } },
    { "type": "INSTALLMENT", "parameters": { "purchaseAmount": 1200000, "months": 12, "feeRate": 0 } }
  ]
}
```

- 각 parameters는 해당 단독 API와 같은 DTO·기본값·검증을 공유한다. 임의 클래스 이름 기반 다형성은 사용하지 않고 type 허용 목록으로 파싱한다.
- COMBINED 중첩, simulationId 참조, 다른 자식 결과 참조·의존 필드는 허용하지 않는다. 구조 자체를 평면으로 제한해 순환과 재귀 실행을 막는다.
- 알 수 없는 type·parameters 필드·의존 필드는 400이다. 중첩 오류는 `scenarios[i].parameters.<field>` 경로를 제공하되 입력 원문은 오류 메시지에 넣지 않는다.
- 입력 순서는 저장 sequenceNo와 지문에 포함한다. 순서를 바꾸면 별도 요청이지만 독립 효과의 합계는 같아야 한다.

### 효과 중복·충돌 방지

자식은 같은 불변 기준선에서 독립적으로 계산한다. 앞 자식의 결과를 다음 자식의 잔액이나 소득으로 사용하지 않는다.

| 충돌 | 처리 |
| --- | --- |
| 정규화된 동일 자식 요청 반복 | 400, 동일 행동 이중 반영 방지 |
| SPENDING 전체 범위와 카테고리 지정 혼합, 같은 카테고리 반복 | 400; 서로 다른 카테고리만 함께 허용하고 총 감소액 상한도 검증 |
| SAVING 2개 이상 | 400; 절대 저축액 교체의 중복 방지 |
| 같은 loanId에 추가상환·대환이 둘 이상 | 유형이 달라도 400; 같은 잔액을 독립적으로 변경하지 않음 |
| 같은 cardId 리볼빙 반복 | 400 |
| cardId 없는 리볼빙이 포함된 다중 리볼빙 | 400; 서로 다른 잔액인지 확인 불가 |

SPENDING과 SAVING은 함께 허용한다. 단, SAVING 입력은 변경 후 절대 저축액이므로 SPENDING 절감액을 목표 저축에 다시 자동 배분하지 않는다.
수수료율 모드는 요청 재사용용 지문에는 포함하지만 동일 행동 충돌 검사에서는 제외한다. 같은 금액·기간의 할부를 생략 수수료율과 명시적 0으로 두 번 넣어 중복 검증을 우회할 수 없다.
다른 상품 가입·신규 차입·할부·현금서비스 입력이 다르면 별개의 가상 행동으로 본다. 자금 출처를 연결하거나 기존 카드 청구·cashflow forecast를 더하지 않는다.

### 합성 결과

- child before/after 수준값, cumulative, comparison 배열, 목표 날짜를 단순 합산하지 않는다.
- 현금흐름은 정규화된 각 자식의 월 delta와 currentMonth.delta를 합한 뒤 cumulative를 처음부터 재계산한다. 전체 기간 종료는 자식 종료 중 최댓값이다.
- 551은 durationMonths까지만 delta가 있고 이후는 0이다. 공통 표시기간은 다음 달부터 최대 120개월이다.
- 585의 120개월 밖 현금흐름을 누락된 0으로 간주하지 않는다. 부모는 같은 표시 상한을 사용하고 자식의 전체 비용·종료일·truncated 정보를 보존한다.
- 리볼빙 미완납이면 `projectionIncomplete=true`를 별도로 제공한다. 표시기간 잘림(truncated)과 실제 완납 여부를 혼동하지 않는다. 종료일을 모르면 fullTermEndDate는 null, 평가 종료일은 details에 둔다.
- 부모 comparison은 같은 단위·기간·의미가 검증된 항목만 집계한다. 유형별 나머지는 details.children에 sequenceNo·type과 함께 보관한다.
- 집계 가능 항목: 기준일 최초 현금·부채 변화와 아래 공통 평가 구간의 이자/수수료 비용. 비용은 `FINANCE_COST_EVALUATED`로 표시하며 평생 총비용으로 표현하지 않는다.
- 초기 변화와 중도 행동일 변화, 누적 원금·이자는 별개다. 날짜가 다른 PREPAYMENT_* 등을 INITIAL_*에 섞거나 초기/행동 항목을 이중 합산하지 않는다.
- 소득 미등록의 null은 0으로 바꾸지 않는다. before/after 공통 기준선 수준값은 참고값으로 유지하고, 부모 cashflow.basis는 SCENARIO_NET_CASH_CHANGE다.
- 참고 기준선 유지는 소득·지출·저축·가용자금 수준값에만 해당한다. 목표 날짜는 §5의 부모 투영 결과 하나로 통일한다. 부모 `after.goals[].expectedAchievementDate`·`after.goals[].monthlySaving`, 목표 관련 comparison 항목, `goalImpacts[].afterForecastDate`·`differenceDays`·`status`·`reasons`는 모두 같은 투영 결과에서 조립하며, 자식의 단독 목표 날짜를 부모 응답의 어느 필드에도 섞지 않는다. §5에서 NOT_COMPUTABLE인 목표는 `after.goals[].expectedAchievementDate`도 null이다. `before.goals[]`는 기준선 그대로다.

### 비용 평가기간과 내부 계산 자료

- 공통 평가 시작일은 기준일, 종료일은 `min(자식별 계산 가능 종료일의 최댓값, 기준일 120개월 뒤가 속한 달의 말일)`이다. 리볼빙 미완납 자식의 종료일은 실제 만기가 아닌 120번째 평가 회차일을 사용한다. 양 끝 날짜를 포함하고 details에 `evaluationFromDate`, `evaluationThroughDate`, `costBasis=PAYMENT_DATE`를 저장한다.
- 각 계산기는 공개 응답 조립 전의 내부 결과에 전후 각각 날짜별 `{date, principal, interest, fee}` 납부 자료를 유지한다. 금액은 확정된 회차 반올림 결과를 사용하며 원금을 비용에 포함하지 않는다. 기준일 유입·원금 이동은 현금 사건으로 따로 유지한다.
- 복합 비용은 평가기간에 **납부일이 포함된** interest+fee를 자식별로 전후 각각 합산하고 `delta=after-before`로 계산한다. 대환·추가상환의 비용 절감은 음수 delta다. 기간 밖 납부액을 일할 안분하거나 발생주의 미지급 이자로 바꾸지 않는다.
- 585의 전체 만기 이자나 120개월로 잘린 순현금 표에서 기간 비용을 역산하지 않는다. 기존 순수 계산에서 생성한 전체 회차 자료(최대 360회)를 내부 결과로 전달하고, 같은 자료로 기존 공개 응답과 복합 기간 비용을 각각 조립한다. 상품 이자 수익은 금융비용에 넣지 않는다.
- 계산 범위 안에서 평가기간보다 일찍 완납된 자식은 이후 비용 0이다. 계산이 끝났어도 미완납인 자식의 이후 비용은 미상이며 0으로 채우지 않는다. 해당 경우 부모에 `costComplete=false`, 자식별 `costCoveredThrough`와 사유를 남기고 합계는 계산된 비용의 부분합임을 표시한다. 자료가 평가기간 전체를 덮으면 costComplete=true다.
- 자식의 만기 전체 비용은 details.children에 기존 의미·기간과 함께 별도로 보존한다. 부모 평가기간 비용과 더하지 않는다. 과거 저장 JSON에는 내부 회차 자료가 없으므로 이를 복합 계산 입력으로 재사용하지 않는다.

## 5. 목표 영향

- 먼저 목표별 remaining≤0을 검사한다. 이미 달성한 목표는 신규 단독·복합 모두 before/after=기준일, differenceDays=0, COMPUTED와 ALREADY_ACHIEVED를 반환한다. 귀속 불명·복합 계산 불가 사유보다 이 처리가 우선한다. 기존 `SimulationScenarios.notComputableGoals`의 예외와 같은 계약이다.
- 신규 할부·리볼빙·현금서비스의 **미달성** 목표는 자금 출처·귀속을 알 수 없다. before 날짜를 보존하고 after/differenceDays=null, NOT_COMPUTABLE과 GOAL_ALLOCATION_UNKNOWN을 반환한다. 목표 없으면 []다.
- 복합이 SPENDING/SAVING만 포함하면 t(k)=기준일.plusMonths(k), k≥1의 월별 투영으로 목표 잔여액을 한 번 계산한다. 각 자식의 변경은 k≤durationMonths인 구간에만 유효하고 종료 후 해당 변경을 제거한다. 마지막 자식 종료 후에는 기준선 목표별 저축속도로 복귀한다.
- 각 k에서 유효한 SPENDING의 감소액만 합쳐 한 번 배분한다. 배분 비중은 기준일 미달성 목표의 remaining으로 고정하고 goalId 오름차순·마지막 목표 나머지 배분을 사용한다. 이미 달성한 목표는 배분에서 제외하며 도중 달성한 목표 몫을 재배분하지 않는다.
- SAVING이 유효한 구간에는 기존 계좌별 대상 목표 선택·절대액 배분 규칙으로 목표별 속도를 교체한다. 해당 구간의 SPENDING 절감액은 목표에 추가 배분하지 않고 `SAVING_AMOUNT_IS_FINAL_TARGET`을 남긴다. SAVING 종료 후에도 SPENDING이 유효하면 그 구간부터 절감액 배분을 다시 적용한다. 이 규칙은 목표 귀속에만 적용하며 현금 delta 합성은 각 자식의 유효기간을 따른다.
- 각 투영일에 `max(0, 해당 목표의 구간 저축액)`을 잔여액에서 차감한다. 최초 잔여액≤0인 t(k)가 after 날짜다. 최대 유효기간 이후 미달성이면 기준선 속도로 필요한 개월 수를 올림해 동일 t(k) 축에서 이어 계산한다. 기준선 속도 0이면 after=null이며 사유를 남긴다. 기존 목표 원금을 인출한 것으로 계산하지 않는다.
- 예: 목표 잔여액 100만원·기존 속도 10만원이고 감소액 합계 10만원이 1개월만 유효하면 첫 달 20만원, 이후 10만원씩으로 9개월째 달성한다. 변경 속도 20만원을 계속 적용한 5개월로 계산하지 않는다.
- 기존 551 단독은 현재 일정 표시기간과 별개로 변경 속도를 지속 적용하는 목표 추정 계약이다. 이번 기간 제한은 새 COMBINED 부모에 적용하며 기존 550·551·585의 단독 계산·공개 응답·저장 결과를 변경하지 않는다. 부모 assumptions에 `GOAL_EFFECT_LIMITED_TO_SCENARIO_DURATION`을 남기고, details.children의 단독 추정 날짜가 부모 합성 날짜와 다를 수 있음을 문서화한다.
- 기간 제한과 목표 귀속 정책을 안전하게 합성할 수 없는 나머지 복합(대환 포함)은 `COMBINED_GOAL_EFFECT_NOT_COMPUTABLE`과 자식의 사유를 반환한다. 자식의 단독 목표 영향은 details.children에서 확인할 수 있다.
- 이 제한은 복합 현금흐름/비용 계산 실패가 아니다. 임의의 합산 달성일을 만들지 않는 586 기본안이며 FE 인계 문서에 명시한다.
- 실행 POST·상세 GET·goal-impact GET은 기존 조립기를 공유한다. 목표 계좌·잔액·이력은 변경하지 않는다.

## 6. 구현 구조와 저장

1. request DTO 4종, 정규화 Input 4종, 자식 요청 허용 목록 파서와 복합 검증기를 추가한다.
2. 기존 Resolver를 재사용해 복합 안의 계좌번호도 내부 ID로 정규화한다. 카드에는 DB 조회 자체에 userId/cardId 조건이 들어가는 소유권 메서드를 추가한다.
3. 지문 재사용 전에 모든 자식의 사용자 자원 존재·소유권을 검증한다. 중복 반환 경로로 소유권 검증을 우회하지 않는다.
4. Runner는 잠금·기준일·기준선·저장을 부모에 대해 한 번 수행한다. 복합 계산이 Runner.run을 재호출하지 않도록 계산기 조회/dispatch를 별도 작은 컴포넌트로 분리한다.
5. SnapshotReader는 자식별 기존 상품·대출 스냅샷을 준비한다. 모든 자식은 같은 기준일을 사용하고 자식 하나라도 실패하면 부모와 자식을 전부 저장하지 않는다.
6. 신규 순수 계산기 3종 → Combined 계산기 순으로 구현한다. 내부 계산 결과에는 날짜별 전후 원금·이자·수수료 자료와 계산 범위/완납 여부를 담고 기존 6종의 공개 응답은 보존한다. 585 일정 생성 로직을 복사하지 않고 같은 계산 자료를 반환하는 내부 경계를 추출한다. COMBINED 목표 투영기는 §5의 기간 제한을 담당하며 기존 단독 투영기를 바꾸지 않는다.
7. 현재 Store는 항상 scenario 1행을 저장한다. 단독은 그대로, 복합은 부모 simulation 1행과 실제 자식 scenario N행(sequenceNo 1~N)을 저장하도록 확장한다. 별도 자식 simulation은 생성하지 않는다.
8. 복합 request/scenario 파라미터에는 정규화된 자식 입력만 저장한다. 원문 계좌번호·카드번호·조회 해시는 JSON 어느 깊이에도 남기지 않는다.
9. 계산 버전을 올린다. 숫자 스케일·기본값 정규화 후 지문을 만든다. 의미가 같은 기본값(예: repaymentMonths 생략/null/1)은 같은 지문이다. feeRate 생략/null은 ASSUMED_ZERO로 서로 같지만, 명시적 0은 EXPLICIT로 다른 지문이다. 명시적 0과 0.0000은 같은 지문이며 적용률·모드를 부모 지문 안의 각 자식에도 포함한다. 585의 AUTO/FULL_BALANCE 모드 구분은 유지한다.
10. 같은 날 동일 요청은 200 created=false, 최초는 201 created=true다. 과거 저장 결과 GET은 재계산하지 않고 기존 JSON 확장 필드 부재도 허용한다.

응답은 기존 최상위 SimulationResponse를 유지한다. details에 calculationPolicy, inputSource, evaluatedThrough, paidOff,
remainingBalance, totalPrincipalPaid, financeCost, repaymentSchedule 등을 유형별로 추가한다.
일정은 날짜 오름차순이며 {date, openingPrincipal, principalPayment, interest, fee, payment, closingPrincipal}로 검산 가능하게 제공한다.
모든 회차에서 `payment = principalPayment + interest + fee`, `closingPrincipal = openingPrincipal - principalPayment`로 고정한다. 유이자 할부의 수수료처럼 내부 자료의 fee가 있으면 그대로 싣고, 수수료가 없는 유형(리볼빙·현금서비스·585 대출 일정 등)은 fee=0으로 제공해 유형에 따라 필드가 빠지지 않게 한다. fee를 interest에 합치거나 payment에서 원금+이자를 뺀 값으로 역산하지 않는다.
복합 details.children도 입력 순서로 제공하고 카드 ID 이외 민감번호는 포함하지 않는다.

## 8. 구현 순서와 완료 기준
