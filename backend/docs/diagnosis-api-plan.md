# Diagnosis 544·545 착수 판단과 구현 계획

작성일: 2026-09-13. 구현 전 계획이며 완료된 기능을 설명하지 않는다.

> 진행 결과는 [diagnosis-api.md](diagnosis-api.md)를 따른다. 아래 내용은 구현 전 계획이며,
> 현재는 7개 API와 목표/현금흐름 규칙을 추가했다. 나머지 규칙·군집 실행은 미완료다.

## 판단과 확인 범위

현재 로컬 develop(`d26ad0a`) 기준으로 설계·API 기반 작업 착수가 가능하다. 엔진 전체 구현은 아래 규칙표의 미정 정책을 확정한 뒤 진행한다. 543의 엔티티·Repository·DiagnosisStore가 있고 Goal 서비스도 존재한다. 544와 545는 공통 계약을 먼저 정하고 544 → 545 순서로 함께 구현하는 것을 권장한다. 문제를 생성하는 규칙과 문제를 조회하는 DTO가 같은 domain/type, 심각도, 근거 JSON을 공유하기 때문이다.

Jira 조회는 403(app is not installed)으로 실패했다. 이슈 범위는 `SPRINT/Jira (4).csv`의 2026-09-07 내보내기와 API 인덱스가 연결한 일반 `14 Diagnosis` CSV를 대조했다. 원격 develop 조회도 네트워크 연결 실패로 최신 여부를 검증하지 못했다. 따라서 최신 Jira 완료 조건과 원격 병합 상태까지 확인한 확정 착수 판정은 아니다.

## 범위

| 이슈 | 구현 대상 |
| --- | --- |
| 544 | POST /api/v1/diagnoses, GET /api/v1/diagnoses, /latest, /{diagnosisId}, /{diagnosisId}/summary |
| 545 | GET /api/v1/diagnoses/{diagnosisId}/issues, /{diagnosisId}/issues/{issueId}; detectionSource·clusterContext 응답 |
| 제외 | 546의 goal-impact·changes, 추천 엔진, 군집 모델 학습·배포 |

군집 결과가 없으면 규칙 기반으로 동작한다는 API·기획안 계약을 따른다. 군집 모델을 새로 만드는 것을 545의 선행 조건으로 두지 않는다. 실제 군집 공급 경로의 존재 여부와 계약은 구현 시작 시 추가 확인하며, 미연동 상태에서는 RULE과 군집 근거 없음으로 반환한다. 합성 군집 통계를 실제 근거처럼 저장하지 않는다.

## 구현 순서

1. **공통 계약 확정**
   - 기획안의 탐지 후보를 기존 도메인 계산 결과와 대조하여 규칙별 입력 출처·조회 기간·임계값·심각도·누락 시 처리를 표로 만든다. 이 규칙 목록 확정이 엔진 구현의 선행 작업이다.
   - domain/type 및 currentValue·benchmarkValue·evidence·clusterContext JSON 형식과 버전을 정한다. 원본 민감번호를 포함하지 않는다.
   - inputSnapshot에 기준시각·타임존, 입력 기간, 데이터 출처/참조 ID뿐 아니라 실제 판정 집계값·단위·적용 임계값·가정·규칙별 실행/제외 사유·규칙 버전을 남긴다. 과거 결과 조회에서 현재 데이터로 재계산하지 않는다.
   - overallStatus 판정과 데이터 부족 표시를 정한다. 입력이 없어 탐지하지 못한 경우를 단순히 건강한 상태로 오인시키지 않는다.
2. **544 실행 서비스**
   - AuthenticatedUserIdResolver와 Goal 소유권 조회를 사용한다. 타인/없는 목표는 DB FK 오류 전에 RESOURCE_NOT_FOUND로 처리한다.
   - 입력 수집 → 규칙 평가 → DiagnosisStore.complete 흐름을 구현한다. 접수·계산·완료의 기존 트랜잭션 경계를 유지한다.
   - 중복 실행 검사는 조회 후 INSERT만으로 해결되지 않는다. 사용자 단위 원자적 접수/잠금 방식을 기존 동시성 구현과 비교해 정한다.
   - forceRefresh 기본값·완료본 재사용 조건·진행 중 요청 응답·접수 만료시간을 문서화한다. 만료된 작업이 늦게 완료될 때의 처리도 검증한다.
   - 실패행은 completedAt=null로 남는 현재 스키마 한계를 유지할지 검토한다. 상태 컬럼 추가가 필요하면 ERD·마이그레이션 변경 필요성을 별도 보고한다.
3. **544 조회 API**
   - 이력·latest·상세·summary를 공통 ApiResponse/PageResponse로 제공한다.
   - 기본 page=0, size=20, 최대 100을 적용한다. latest의 goalId 선택 필터와 소유권을 검증한다.
   - 이력을 포함한 결과 조회는 완료본만 노출하는 기본안을 적용한다. 최신 완료본 없음은 RESOURCE_NOT_FOUND, 목록 없음은 빈 페이지로 구분한다.
   - summary는 저장된 문제와 집계값을 사용하여 545 목록과 일치시킨다.
4. **545 문제 조회 API**
   - 상위 진단의 소유권·완료 여부를 검증하고 문제 조회에도 사용자·진단·문제 ID 조건을 유지한다.
   - domain/type/severity 필터와 페이지를 제공한다. 심각도 내림차순 + issueId 오름차순 기본안에 맞춰 현재 Repository의 issueId 정렬을 DB 페이지 조회 단계에서 변경한다.
   - RULE/CLUSTER/RULE_AND_CLUSTER, 현재값·기준값·근거를 저장된 값으로 변환한다. 군집 근거의 null/생략 규칙을 고정한다.
   - 군집 근거는 아래 노출·병합 계약을 적용한다. 모델 실패나 근거 부적격은 규칙 결과를 유지하며, 같은 카테고리의 문제를 중복 집계하지 않는다.
5. **검증과 문서화**
   - 규칙 경계값·입력 부족·0으로 나누기·금액 정밀도, 실제 생성 → 상세/summary/issues 조회 일치 테스트.
   - 인증 실패, 타인 목표/진단/문제, 다른 진단의 issueId, 잘못된 입력·필터·페이지, 빈 결과 테스트.
   - 중복 요청·forceRefresh·실패 후 재시도·만료·완료본 불변성과 군집 없음/있음의 응답 테스트.
   - 관련 테스트 후 전체 test 및 clean build, git diff --check. MySQL JSON/FK·잠금 검증은 H2 결과와 별도로 기록한다.
   - backend/docs/diagnosis.md와 remaining-work.md를 실제 구현에 맞게 갱신한다.

## 기존 문서·코드 차이

- diagnosis.md는 Goal 엔티티가 없던 543 시점 설명을 포함하지만 현재 GoalService가 있다. 소유권 검증은 현재 Goal 구현을 기준으로 연결한다.
- DiagnosisStore.start 주석은 미완료행을 조회 대상에서 제외한다고 설명하지만 이력 Repository는 completedAt 조건 없이 조회한다. API를 만들 때 노출 정책에 맞게 쿼리와 문서를 일치시켜야 한다.
- API 명세는 상세 DTO, 규칙 임계값, forceRefresh 재사용 기간, 실패 상태 응답을 정하지 않는다. 위 제안은 서비스 기본안이며 구현 전 계약표에서 확정해야 한다.

## 작업 단위

설계와 통합 검증은 544·545를 묶고, 변경은 공통 계약/544 실행·조회/545 문제 조회 순서로 구분한다. 브랜치 생성 단계에서는 최신 Jira 범위와 develop을 재확인하고 Jira Create branch 규칙을 따른다. 이번 검토에서는 브랜치·이슈 상태·기능 코드를 변경하지 않았다.

### 군집 노출·병합

기획안의 다음 조건을 **모두** 충족해야 군집 근거를 노출한다.

1. 군집 표본 수가 최소 기준 이상.
2. 사용자 데이터가 3개월 이상.
3. 분류 신뢰도(중심점 거리)가 허용 범위 이내.
4. 가중 범위 이탈 점수가 임계값 이상.

기획안 계산식은 특징별 범위 이탈을 `scale=max(max-min, 표준편차)`로 나누어 가중 합산한다. 표본 최소값·거리 허용값·특징 가중치·점수 임계값은 문서에 없으므로 공급자 계약으로 확정하며, scale=0·누락·비정상 범위·모델 버전 없음은 부적격으로 처리한다. 범위 이탈만으로 낭비라고 표현하지 않는다.

규칙 문제와 같은 카테고리의 군집 신호는 새 문제를 만들지 않고 근거를 병합해 RULE_AND_CLUSTER로 저장한다. 기본 병합 범위는 동일 진단·소비 카테고리이며, 같은 카테고리의 규칙 문제가 여러 개면 어느 문제에 연결할지 결정적인 우선순위를 규칙표에 추가한다. 군집 단독 문제는 CLUSTER로 저장한다. 집계는 병합이 끝난 최종 문제 목록으로 계산한다. 문제 대응용 ruleKey·대상 ID·categoryId는 근거 JSON에 남겨 향후 546 비교에서 자동 증가 issueId에 의존하지 않게 한다.

작은 표본·모델 실패·불완전한 근거는 RULE 결과를 유지한다. RULE의 clusterContext/modelVersion은 null을 기본안으로 한다. 모델 공급자가 없는 동안 학습·점수 엔진 완료를 주장하지 않으며, 저장된 CLUSTER/RULE_AND_CLUSTER 조회는 테스트 fixture로 별도 검증한다.

### API와 실행 정책 기본안

- 동기 실행을 기본으로 한다. POST 새 완료본은 201, 재사용 완료본은 200, 같은 사용자의 활성 실행은 409를 제안한다. forceRefresh 기본 false이며 활성 실행을 우회하지 않는다. 전용 오류 코드는 기존 ErrorCode 체계에 추가하고 계약표에 이름을 기록한다.
- 접수 직렬화는 사용자 DB 행의 비관적 잠금 아래 활성행 확인과 start를 짧은 트랜잭션으로 묶는 방안을 우선 검증한다. 계산 동안 DB 잠금을 유지하지 않는다. 프로세스 내부 락만으로 다중 인스턴스 보호를 주장하지 않는다.
- 완료본 재사용은 동일 사용자·동일 goalId(null 포함)·동일 ruleVersion·동일 서비스일에 한정하는 기본안이다. goalId 생략 POST는 전체 금융 진단이며 목표 규칙 대상은 삭제되지 않은 활성 목표로 제안한다. latest의 goalId 생략은 기존 Repository대로 사용자 전체의 최신 완료본이므로 재사용 조회와 구분한다. 당일 변경 데이터의 즉시 반영은 forceRefresh가 담당하고 응답 기준시각으로 한계를 알린다.
- 접수 만료시간 수치는 실제 실행 경로·타임아웃 확인 후 확정한다. 완료 직전 같은 사용자 잠금 아래 접수의 유효성·더 최신 실행 존재·DB의 완료 여부를 재검사한다. 만료/대체된 실행의 늦은 완료는 거절하며, detached 객체의 isCompleted 검사만으로 불변성을 보장하지 않는다.
- 실패한 접수행은 결과 조회에서 제외한다. 재시도 차단을 피하기 위한 실패 접수 정리 정책을 구현 전에 확정한다. 기존 discardIssues만으로는 활성 접수행이 남으므로 충분하지 않다. 상태 컬럼 신설은 기본안에 포함하지 않으며, 헤더 정리 등 스키마 유지 방안을 먼저 검토한다.
- 이력·상세·summary·issues는 완료본만 반환한다. 없는/타인/미완료 진단은 RESOURCE_NOT_FOUND, 소유한 완료 진단의 문제 없음은 빈 페이지로 구분한다. 이력은 createdAt DESC, diagnosisId DESC; latest는 completedAt DESC, diagnosisId DESC다.
- issues는 CRITICAL > HIGH > MEDIUM > LOW, issueId ASC로 DB 페이지 조회에서 정렬한다. domain/type은 대문자 코드 형식과 길이 50 이내를 검증하고 형식상 유효한 미등록 값은 빈 결과, severity 미등록 값은 400을 기본안으로 한다.
- 새 실행의 goalId는 삭제되지 않은 본인 목표를 검증한다. 실행 후 목표가 수정/삭제돼도 기존 진단은 저장된 스냅샷으로 조회한다. 목표 생명주기 정책을 과거 진단 소유권과 혼동하지 않는다.

### 데이터 부족·스냅샷·응답

기본 응답에는 diagnosisId·goalId·createdAt·completedAt·ruleVersion·overallStatus·issueCount·highSeverityCount를 둔다. 상세/summary에 coverage(규칙별 평가/제외 사유)와 assumptions를 포함해 문제 0건과 평가 불가를 구분한다. summary의 도메인/심각도별 집계는 필터 전 전체 저장 문제 기준이며, 원본 스냅샷을 그대로 외부에 노출하지 않는다.

평가 가능한 문제에 HIGH/CRITICAL이 있으면 RISK, LOW/MEDIUM만 있으면 CAUTION을 기본안으로 한다. 적용 대상 규칙을 모두 평가했고 문제 0건이면 HEALTHY다. 부분 평가·전부 평가 불가에서 문제 0건이면 overallStatus=null과 coverage 사유를 반환하는 기본안으로 하여 건강 판정을 피한다. 이는 ERD가 허용하는 null을 활용하며 새 상태 enum을 추가하지 않는다. 대상 자산 없음과 수집 실패/이력 부족은 서로 다른 제외 사유다.

스냅샷은 판정에 실제 사용한 수치와 기간을 보존한다. 서로 다른 도메인 응답의 기준일이 달라지지 않도록 진단 Clock을 한 번 읽고 가능한 계산 경로에 전달한다. 원본이 수정될 수 있으므로 참조 ID만으로 재현 가능하다고 보지 않는다. 동기화 시각과 계산 시각을 구분하고, 기존 도메인의 complete/unavailableReasons를 누락 없이 전파한다.

### 추가 완료 조건

- 규칙표의 미정 항목에 구현/후속 이슈/미지원 사유가 결정되어 있고, 미지원 규칙이 coverage에서 구분된다. 임계값 없는 후보를 임의 수치로 탐지하지 않는다.
- 군집 조건 4종 각각의 미충족, scale=0, 같은 카테고리 병합 후 issueCount/highSeverityCount 일치 검증.
- 양수/0/미등록 소득, 현재 월 대출 총액 미확정, 과거 이력 부족, 예측 누락을 정상 0으로 치환하지 않는 테스트.
- 두 동시 접수, forceRefresh 중복, 만료 후 재접수와 옛 실행의 늦은 완료, 실패 직후 재시도 검증. 잠금 동작은 MySQL에서 별도로 확인.
- 목표 수정/삭제·거래 수정 후 과거 상세/summary/issues 불변성, 전체 요약과 필터된 목록의 집계 범위 차이 검증.
- 구현 전 7개 API DTO·상태코드와 위 기본안을 backend/docs/diagnosis.md에 확정 계약으로 옮긴다. 최신 Jira 범위 미확인과 규칙 미정이 남으면 전체 기능 완료로 보고하지 않는다.
