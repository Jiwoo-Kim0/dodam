# 소비 예측 모델 재사용 설계안 — 이번 달 예상 소비와 현금흐름

- Jira: **미발급**. 이슈를 만들 때 키를 채운다.
- 작성일: 2026-09-25 (rev.1)
- 상태: 설계. 코드·데이터 변경 없음.
- 선행: [timeseries-forecast-plan.md](timeseries-forecast-plan.md)(706 설계·seed), [spending-forecast.md](spending-forecast.md)(현재 계약)

706이 만든 월별 변동 소비 예측은 지금 **리포트의 "예상 소비" 카드 하나에만** 쓰인다. 모델은 그 사용자의 계절
계수와 추세를 이미 추정해 두었는데, 앱의 다른 자리에서는 **그보다 나쁜 방법으로 같은 질문에 답하고 있다.**
이 문서는 그 자리 둘을 옮기는 설계다.

## 0. 목적과 범위

| 이 이슈에서 한다 | 뺀다 |
| --- | --- |
| 이번 달 예상 소비를 예측 모델로 계산(적용 1) | 예측 결과 저장·실행 API(`V45` 3테이블) |
| 현금흐름 곡선에 급여 INFLOW와 예측 지출 주입(적용 2) | 카테고리별 예측 분해 |
| 두 적용에 필요한 기준 달 예측 노출 | 목표 저축 속도 배율(706 부록 A) |
| 굳힌 스냅샷 재촬영 범위 확정 | 알림·푸시 연동 |

**시연(2026-09-28) 전에는 착수하지 않는다.** 둘 다 굳힌 진단 스냅샷과 효율 점수에 번지는 변경이다.

## 1. 결정 사항

| 항목 | 결정 | 근거 절 |
| --- | --- | --- |
| 적용 순서 | **적용 1 먼저.** 영향 범위가 좁고 되돌리기 쉽다 | 3, 4 |
| 기준 달 예측 | 계산기에 노출하되 **응답 DTO는 그대로 둔다** | 2 |
| 이번 달 식 | 대체가 아니라 **실적 + 잔여 일수 투영** | 3.2 |
| 축 불일치 | 예측(변동)에 **고정비를 조립**해 전체 소비 축으로 맞춘다 | 3.1 |
| 폴백 | 예측이 없으면 **현행 선형 외삽으로 되돌린다** | 3.3 |
| 현금흐름 주입 | `CashflowEventCollector.collect()` **밖**에서 한다 | 4.2 |

## 2. 선행 문제 — 모델이 이번 달을 예측하지 않는다

`SpendingForecastCalculator.forecast()`는 `for k = 1..horizonMonths`로 돌며 `baseMonth.plusMonths(k)`를 만든다.
기준 달은 **아직 끝나지 않아 추정 입력에서 빠지고 예측 구간도 아니다.** 그런데 이 문서의 두 적용은 모두
"이번 달"을 묻는다.

계산 자체는 막혀 있지 않다. 투영은 `h = ChronoUnit.MONTHS.between(last, target)`로 재고 `last`는 기준 달의
직전 달이므로, `target = baseMonth`면 `h = 1`로 식이 그대로 성립한다. **막혀 있는 것은 인터페이스뿐이다.**

| 선택지 | 판단 |
| --- | --- |
| (a) `forecast()`가 `k = 0`부터 만들게 한다 | **채택.** 식이 이미 성립하고 호출부가 필요한 달을 고른다 |
| (b) `currentMonth()` 메서드를 따로 둔다 | 같은 식을 두 곳에 두게 된다 |
| (c) horizon을 1 늘려 받고 첫 달을 떼어 쓴다 | 응답에 기준 달이 섞여 화면 계약이 깨진다 |

**응답 DTO는 바꾸지 않는다.** [spending-forecast.md](spending-forecast.md) §2가 "기준 달은 `history`에도
`forecasts`에도 없다"를 계약으로 적었고, 화면의 "오늘" 세로선이 그 빈자리에 선다. 기준 달 예측은 서버 내부
계산에만 쓴다.

## 3. 적용 1 — 이번 달 예상 소비(`projectedMonthEnd`)

### 3.1 지금은 선형 외삽이다

`GoalCalculationService.SpendingContext.projected()`:

```
projected = spent × 그 달 일수 ÷ 경과 일수
```

월초에 크게 튄다. 1일에 10만 원을 쓰면 310만 원으로 잡힌다. 주말·급여일 쏠림도 보지 못한다.

**축이 다르다는 점을 먼저 풀어야 한다.** 이 식의 `spent`는 `JdbcSpendingAnalysisReader.readSpendingTotal()`이고
그 정의(`JdbcSpendingReader.SPENDING_WHERE`)는 **고정비를 포함한 전체 소비**다(`EXPENSE` 중 `NON_SPENDING`만
제외, NULL은 소비로 봄). 반면 706 모델이 예측하는 것은 **변동 소비뿐**이다. 그대로 갖다 쓰면 고정비가 통째로
빠진 숫자가 된다.

706 계획서 §4가 이미 "변동 소비 V 하나만 예측하고 나머지는 조립"으로 정해 두었다. 조립할 고정분은 그 달의
확정 스케줄(고정비·구독·대출 상환)에서 온다 — 적용 2가 쓰는 것과 같은 원천이다. **두 적용이 같은 조립 코드를
공유해야 하고, 그래서 적용 1을 먼저 하더라도 조립은 공통 자리에 둔다.**

`predicted_total`은 706에서 "응답에 싣지 않는다"로 닫힌 항목이다(계획서 §9-2). 그 결정은 **응답에 대한 것**이고
내부 계산으로 쓰는 것까지 막지 않는다. 다만 닫은 이유였던 "고정비 펼침 오차가 측정되지 않는다"는 그대로
남으므로, §6에서 그 오차를 먼저 잰다.

### 3.2 바꿀 식

```
변동 예측 잔여 = max(0, 기준 달 변동 예측 × (남은 일수 ÷ 그 달 일수))
고정 예측 잔여 = 남은 기간의 확정 스케줄 합
projected = max(spent, spent + 변동 예측 잔여 + 고정 예측 잔여)
```

- **대체가 아니라 실적 + 잔여다.** 이미 쓴 돈은 예측보다 실적이 정확하다. 월말로 갈수록 실적에 수렴하고
  월초 과장이 사라진다.
- 변동분을 남은 일수로 **균등 배분**한다. 일 단위 계절성(주말 쏠림)은 706 모델이 갖고 있지 않다. 그것까지
  하려면 일별 모델이 필요하고 이 이슈 범위 밖이다.
- 하한을 `spent`로 둔다. 이미 예측 합계를 넘겨 쓴 사용자의 예상치가 실적보다 작아지면 안 된다.

### 3.3 예측이 없을 때

`fallbackReason`이 `USER_DATA_TOO_SHORT`·`FEATURES_UNAVAILABLE`이면 예측이 없다. 이때는 **현행 선형 외삽으로
되돌린다.** 폴백을 두지 않으면 이력이 짧은 사용자의 소비 목표 진단이 통째로 빈다.

### 3.4 바뀌는 화면

| 화면 | 값 | 어떻게 바뀌나 |
| --- | --- | --- |
| 목표 상세(소비) | `expectedSavingAmount` = `max(0, 전월 소비 − projected)` | 월초에 0으로 눌려 있던 값이 살아난다 |
| 목표 상세(소비) | `usageRatePercent`·상태 배지 | 월초 "초과 예상" 오판이 준다 |
| 데일리 브리핑 | 같은 `expectedSavingAmount` | 매일 보는 자리라 체감이 가장 크다 |
| 발견(진단·추천) | `SPENDING_GOAL_RISK` 판정, `REDUCE_SPENDING`의 `monthlyCostSaving` | **문제·추천 건수가 줄 수 있다** |

마지막 줄이 이 적용의 실제 위험이다. 시연 시나리오가 진단 건수에 의존하면 그림이 달라진다.

### 3.5 굳힌 스냅샷

진단은 `projectedMonthEnd`를 스냅샷에 굳히고 추천이 그 값을 읽는다(`DiagnosisGoalImpactService`,
`DiagnosisChangeService`가 전후 비교에 쓴다). 정의가 바뀌면 옛 정의로 굳은 행과 섞인다. 694에서 겪은 것과
같은 종류다. **재촬영 범위를 착수 전에 정한다** — 최소한 `improvement_action.before_snapshot`과 완료된 진단의
`currentValue`가 대상이다.

## 4. 적용 2 — 현금흐름 곡선

### 4.1 지금은 들어오는 돈이 없다

`CashflowEventCollector`가 `List<AccountScheduledEventSource>`를 주입받는데 **구현체가 하나도 없다**(인터페이스만
있다). 그래서 예측 곡선에 수입이 전혀 들어가지 않고 잔액이 단조 감소한다. 706 부록 A가 "이것만으로도 예측
정확도가 오른다"고 적어 둔 자리다.

`payday`가 1~31이라 말일 당김 규칙이 필요하다(2월 31일은 없다).

### 4.2 주입은 `collect()` 밖에서

`UpcomingExpenseService`가 **같은 `collect()`** 를 불러 "다가오는 지출"을 만든다. 예측 지출을 `collect()` 안에
넣으면 추정치가 확정 예정처럼 화면에 뜬다. 예정 비용은 지금 `partial: true`와
`ACCOUNT_SCHEDULE_SOURCE_UNAVAILABLE` 경고로 **스스로 과소집계임을 밝히고 있는데**, 그 경고가 사라지면서 값만
부정확해지는 최악이 된다.

- 급여 INFLOW는 `AccountScheduledEventSource` 구현체로 넣는다. 확정 스케줄이 맞다.
- **변동 소비 예측은 `collect()`가 아니라 예측 조립 단계에서 더한다.** 예정 비용은 지금 계약을 유지하되,
  별도 항목으로 노출할지는 §7 미결이다.

### 4.3 효율 점수가 같이 움직인다

`EfficiencyScorePolicy`의 `CASHFLOW` 항목은 "그 달 말일 기준 마지막 예측의 위험"에서 나오고
`100 − Σ(CRITICAL 40, HIGH 30, MEDIUM 15, LOW 5)`다. 급여 INFLOW가 들어가면 잔액 부족 위험이 줄어
**점수가 올라간다.** 예측 구분 컬럼으로는 걸러지지 않는다.

리포트 상단 점수와 발견 화면 진단이 같이 흔들린다는 뜻이다. 694가 만든 `efficiency-v3` 정의에 손대지 않고도
값이 바뀌므로, **점수 변화가 모델 교체 때문임을 리포트에 남길지**를 §7에서 정한다.

### 4.4 바뀌는 화면

| 화면 | 값 | 어떻게 바뀌나 |
| --- | --- | --- |
| 홈 | 오늘부터 14일 `cashflow/events` | 단조 감소 곡선이 급여일에 올라간다 |
| 데일리 브리핑 | 같은 이벤트 | 같은 변화 |
| 리포트 | 효율 점수 `CASHFLOW` 항목 | 위험이 줄어 점수가 오른다 |
| 리포트 | 예정 비용 | 계약 유지. §7 결정에 따라 항목이 는다 |

## 5. 발견한 불일치 — `hidden` 필터

이 조사에서 나온 별건이다. `JdbcSpendingReader.SPENDING_WHERE`는 숨긴 거래(`hidden = TRUE`)를 소비에서 빼는데,
`JdbcSpendingForecastReader`의 조회 조건에는 **`hidden` 절이 없다.** 예측 입력에는 숨긴 거래가 들어간다.

706 단독으로는 드러나지 않았다. 예측 카드가 다른 소비 숫자와 나란히 놓이지 않았기 때문이다. 적용 1은 같은
화면에서 두 정의를 더하므로 **반드시 맞춰야 한다.** 시연 seed에는 `hidden = TRUE` 행이 없어 값은 안 바뀐다.

## 6. 검증

- **고정비 펼침 오차를 먼저 잰다.** 706 §9-2가 `predicted_total`을 닫은 이유다. 확정 스케줄로 조립한 고정분과
  실제 그 달 고정비 합계를 지난 12개월에 대해 비교해 오차를 수치로 남긴다. 이 수치 없이는 조립값을 화면에
  내보내지 않는다.
- 적용 1: 지난 12개월에 대해 **월중 각 시점의 예상치와 실제 월말 합계**를 비교한다. 현행 선형 외삽과 나란히
  놓아 월초 구간의 개선을 보인다. 개선이 없으면 이 적용은 하지 않는다.
- 적용 2: 급여 INFLOW 주입 전후로 `CASHFLOW` 항목 점수 변화를 U0003으로 측정해 기록한다.
- MySQL 실측: 조립 쿼리가 새로 생기면 `JdbcSpendingForecastReaderMySqlIntegrationTest`와 같은 게이트 방식으로
  덮는다. H2 통과로 대체하지 않는다.

## 7. 미결

1. **소비 목표의 축을 바꿀 것인가.** 조립 대신 소비 목표 자체를 "변동 소비 기준"으로 바꾸면 조립이 필요 없어진다.
   다만 사용자가 예산을 잡을 때 고정비를 빼고 생각하는지는 확인된 바 없다. 기획 결정이다.
2. **예정 비용에 예측 항목을 노출할 것인가.** 노출하면 `partial` 경고를 걷을 수 있지만, 확정과 추정이 한 표에
   섞인다.
3. **효율 점수 변화를 사용자에게 설명할 것인가.** 점수가 오르는 이유가 사용자의 개선이 아니라 모델 교체다.
4. **재촬영 범위.** 3.5의 굳힌 스냅샷 중 어디까지 다시 찍을지.

## 8. 위험

1. **진단 건수가 준다.** 3.4 마지막 줄. 시연 시나리오가 건수에 의존하면 그림이 달라진다.
2. **예측 성능은 여전히 검증된 바 없다.** 지금 데이터는 시연용 합성 데이터이고, 706 §7.2가 "그 수치는 모델
   성능이 아니다"를 명시했다. 더 많은 화면이 이 모델에 의존할수록 그 문장이 더 중요해진다.
3. **사용자 단위 계절 추정은 실거래에서 흔들린다.** 계수 12개를 2주기로 추정하는 구조다. 화면 두 곳이 더
   붙으면 인구 단위 학습으로 되돌릴 때 손댈 곳도 는다.
4. **두 적용이 같은 조립 코드를 공유한다.** 적용 1만 하고 멈추면 그 코드가 호출부 하나짜리로 남는다. 나쁘지는
   않지만, 적용 2를 안 할 거라면 조립을 공통 자리에 둘 이유도 없다.
