## 3. 계산 정책 제안

### 공통

- 기준일은 서버 Asia/Seoul 날짜를 실행 중 한 번 얻는다. 금액은 long, 금리 계산은 BigDecimal이다. 대출은 회차별 원 단위 HALF_UP과 마지막 회차 잔액 보정, 예적금은 전체 이자 합산 후 원 단위 절사를 적용한다(536·537 계약).
- 상품은 저장된 상품·옵션과 syncedAt을 사용한다. 실제 적용 금리, 옵션 ID, 상품 기준 시각과 선택 근거를 결과에 저장한다.
- 우대금리 자동 적용을 하지 않는다. 기간·상품 유형·상환방식을 만족하는 옵션을 먼저 고르고, 중복 옵션은 명시적인 정렬 정책으로 결정한다. 대출에 범위 금리만 있으면 하한 기반 추정임을 표시한다. 필수 금리 누락은 0%로 대체하지 않는다.
- 예적금은 option.rate, 대출은 option.minRate를 기준으로 한다(536·537·533). 대출 하한은 예상 승인금리가 아니라 공시 최저금리 시나리오다. 상품 옵션의 상환 코드와 Loan enum은 다르므로 533의 대응표를 사용한다. AMORTIZING은 두 균등 방식에 대응해 생략 시 하나로 확정할 수 없으며, CREDIT_LINE·OVERDRAFT는 이번 분할상환 모델에서 제외한다. 변동금리도 현재 공시금리 고정이라는 가정을 표시한다.
- 본인 대출은 LoanRepository의 사용자·계좌번호 HMAC 조건으로 조회한다. 계좌번호 원문·해시는 요청 스냅샷이나 결과에 저장하지 않는다.
- 현재 대출 데이터는 로컬 스냅샷을 사용한다는 제안이다. API 명세의 추가상환 `SSAFY + 자체`와 차이를 구현 문서에 기록한다. 요청 중 외부 금융망 호출은 추가하지 않는다.
- 중도상환 수수료·대환 부대비용 자료가 없어 기본 계산은 비용 제외 추정치로 제공한다. 수수료 0원 확정이나 확정 절감액으로 표현하지 않는다.

### 예적금 신규가입

- 입력: productId, monthlyAmount, term. 기간별 옵션 존재와 상품 유형(DEPOSIT/SAVINGS)을 검증한다.
- 적금은 monthlyAmount를 월 납입액으로 해석한다. 예금은 같은 필드를 일시 예치 원금으로 해석하는 안이며, 명세의 필드명이 모호하므로 구현 전 계약에 명시한다.
- 단리·ACT/365, 예금은 기준일 일시 예치, 적금은 기준일 첫 납입 후 term회 월별 납입(만기일 납입 제외)으로 제안한다. 적금 이자는 각 회차의 납입액×실제 예치일수를 합산한 뒤 계산한다. 말일은 최초 약정일 기준으로 복원한다.
- ERD에는 복리 주기·이자 지급 방식 컬럼이 없어 복리 여부를 조회해 거부할 수 없다. 단리는 서비스 추정 모형임을 표시한다. saving_type으로 식별 가능한 연동형·회전형·연금형 상품을 일반 확정금리 예금처럼 계산하지 않도록 지원 유형 목록을 구현 전에 고정한다(536의 비교군 참조).
- 세전 이자를 공통 비교 기준으로 제공하고 세금 제외 가정을 표시하는 안이다. 기존 예금 상세의 세후 수령액과 직접 비교하지 않도록 명시한다.
- 예치 원금 이동을 수익으로 세지 않는다. 원금, 이자, 만기 수령액, 납입에 따른 가용현금 변화를 분리한다.

### 신규 대출

- 입력: productId, principal, term, repaymentType?. 원금·기간·상품 유형·한도·상환방식을 검증한다.
- repaymentType 생략 시 유일하게 선택 가능한 상품 옵션만 자동 선택한다. 여러 방식이 가능하면 명시 입력을 요구한다.
- 첫 상환일은 기준일 다음 달의 같은 날짜(말일 보정), 만기는 term개월 후로 제안한다. 기존 LoanRepaymentScheduleCalculator의 일정 생성·회차 수와 대조한다.
- 대출 원금 유입과 부채 증가를 함께 반영한다. 차입금을 소득·수익으로 계산하지 않는다.

### 추가상환

- 입력: accountNo, prepaymentAmount, paymentDate?. 날짜 기본은 기준일, 금액은 양수이며 실행일의 예상 잔액 이하로 제한한다.
- 과거 실행일, 만기 후 실행일, 오래된 다음 상환일·필수 조건 누락은 명시적으로 거부한다.
- 미래 paymentDate까지 기존 약정 상환을 먼저 반영한 뒤 추가상환한다. 같은 날짜의 약정 상환 후 추가상환 순서를 고정한다.
- 기본안은 만기 유지·남은 월 상환액 재계산이다. 만기 단축 방식은 별도 입력이 없으므로 제공하지 않는다.
- 월이율 모형에서 월중 추가상환의 일할이자 미반영 가정을 드러낸다. 전액 상환, 만기 당일, 첫 회차 전후를 독립 검증한다.

### 대환

- 입력: accountNo, targetProductId, refinanceAmount?. 금액 생략 시 기존 잔액 전액, 명시 시 0 초과·잔액 이하이다.
- 잔여 만기와 기존 상환방식을 유지하고 대상 상품이 해당 조건을 지원하는지 확인하는 안이다. 지원하지 않는 기간을 임의의 근접 옵션으로 대체하지 않는다.
- 단, 533 후보는 정확 기간이 아닌 기간 밴드로 선정한다. 따라서 후보 productId를 전달해도 잔여 기간 옵션이 없어 실행이 거부될 수 있다. 비교 가능과 계약 조건 지원은 다르다. 이 계획은 정확 옵션이 없으면 계산 불가로 처리하는 보수적 안을 유지하되, 후보→대환 성공 예제와 불가 사유를 FE에 함께 제공한다. 기간 밴드 금리를 차용하려면 별도 추정 정책으로 문서화해야 한다.
- 부분 대환은 기존 대출 잔여분과 신규 대출분을 따로 계산한 뒤 합산한다. 기존 잔액 전체를 신규 금리로 바꾸지 않는다.
- 대환 원금 유입·기존 원금 상환은 상쇄되며 비용·상환 일정 변화만 순효과로 계산한다.

## 4. 데이터·구조 설계

1. 요청 DTO 4종과 정규화 입력 4종을 추가한다.
2. 상품·대출 조건을 불변 스냅샷으로 읽는 Reader를 simulation 경계에 둔다. 상품/대출 엔티티를 순수 계산기에 넘기지 않는다.
3. Runner의 사용자 잠금 안에서 기준선과 신규 스냅샷을 읽는다. 기존 두 유형이 새 Reader를 필요로 하지 않도록 유형별 준비 단계를 둔다.
4. 정규화된 요청 기준의 같은 날 재사용 정책은 유지한다. 재사용 결과는 저장 당시 데이터임을 명시한다. 소유권 확인은 재사용 반환 전에도 수행한다.
5. 계산기 4종을 추가하고 기존 LoanRepaymentTerms·LoanRepaymentScheduleCalculator를 조합한다. 기존 계산기의 누락값을 0으로 처리하는 동작 앞에 필수 조건 검증을 둔다.
6. 상품 계약기간과 현금흐름 표시기간을 분리한다. 기존 SimulationInput의 120개월 상한을 대출 만기에 무조건 적용하지 않는다. 대출 계산은 최대 360회, 표는 최대 120개월 안으로 제한하고 잘림을 표시하는 안이다. 전체 이자 계산이 잘렸다면 총액으로 표시하지 않는다.
7. 기존 응답의 최상위 구조를 유지하고 comparison·cashflow·assumptions에 유형별 항목을 추가한다. 기존 spending/saving 저장 결과도 계속 조회 가능해야 한다.

## 5. 현금흐름·목표 영향

- 기존 월 소비·목표 저축 기준선은 전체 자산·부채 현황이 아니다. 신규 유형에서 필요한 대출 일정과 현금 변화를 따로 계산한다.
- 시작일 일시금과 다음 달 이후 월별 변화를 분리해 시작일 현금 유출을 누락하지 않는다. 현금흐름 forecast 이벤트를 다시 더하지 않는다.
- 예치 원금은 자산 내 이동, 대출 원금은 현금과 부채 동시 증가, 상환 원금은 현금과 부채 동시 감소로 처리한다.
- 목표는 실제 저장값을 변경하지 않는다. 월별 절감액은 남은 목표 금액 비례 배분이라는 기존 가정을 재사용하되, 시작일 유출·만기 유입·유한 기간을 반영하는 월별 투영으로 확장한다.
- 시작일 지출의 출금계좌와 목표 연결이 입력에 없으므로 특정 목표 잔액에서 임의 차감하지 않는다. 자금 배분은 서비스 가정으로 표시하고, 정보 부족 시 예상 달성일 null과 사유를 반환한다. 신규 차입금을 자동으로 목표 저축으로 간주하지 않는다.
- 목표 투영 기간과 현금흐름 표의 120개월 상한은 분리한다. 상한 밖이라는 이유로 기존에 유효한 목표 예상일을 null로 바꾸지 않는다. 변화가 없으면 기존 before 날짜를 그대로 보존한다. 월별 변화가 끝난 뒤에는 기존 저축속도로 남은 금액을 계산하는 안을 검토하고, 속도 0·자금 출처 불명 등 실제 계산 불가일 때 null과 사유를 제공한다.
- 신규 적금 납입을 목표 자산 축적과 가용현금 감소에 모두 동일 부호로 더하지 않는다. 이미 기준선의 목표 저축속도에 포함된 납입인지 알 수 없으므로 신규 납입의 추가성·목표 귀속 가정을 고정해야 한다. 기존 목표 원금을 옮기는 예금 가입과 외부 여유자금으로 가입하는 경우도 구분할 근거가 없다. 무조건 달성일을 계산하는 대신 계산 가능한 목표와 불가 사유를 분리하고, 정상 시나리오에서 실제 목표 영향이 산출되는 예제를 완료 조건에 포함한다.

## 6. 구현 순서와 검증

1. 위 정책 중 모호한 입력 의미·금리·세금·상환일·대환 옵션·목표 투영을 구현 계약과 예시 응답으로 고정한다.
2. Reader/요청 검증/스냅샷 준비를 추가한다.
3. 신규 대출 → 추가상환 → 대환 순으로 대출 계산을 완성한다. 예적금 계산을 추가한다.
4. 공통 저장·조회·현금흐름·목표 영향에 연결하고 simulation.md를 갱신한다.
5. 계산 단위 테스트: 손계산 가능한 예제, 0% 금리, 원금 보존, 마지막 잔액 0, 부분·전액 상환, 같은 금리 대환, 말일·윤년, 금액 오버플로, 잘림·조건 누락을 검증한다.
6. API 테스트: 4종 정상, 400/401/404, 타인 대출, 실패 시 저장 없음, 같은 날 재사용, 민감번호 미노출, 저장 이후 상품 변경에도 조회 불변, 기존 두 유형 회귀를 검증한다.
7. 일회용 MySQL에서 V19 JSON·복합 FK·실제 조회를 검증한다. 새 DB의 V6→V11 의존 문제를 우회해 전체 Flyway 기동 성공으로 보고하지 않는다. 재현 시 선행 결함으로 별도 기록한다.
8. 관련 테스트 → 전체 test → clean build → git diff --check. 미실행 항목과 환경 원인을 보고한다.

## 10. 구현할 상세 계약

사용자가 기본안을 맡겨 진행하도록 요청한 데 따라 아래 정책으로 구체화했다. 기준 명세가 정한 사실과 서비스가 보완한 계산 정책은 구분하며, 실제 구현 후 simulation.md에 옮긴다.

### 10.1 요청과 범위

모든 POST는 인증 필수다. 사용자 ID는 토큰에서 얻는다. 신규 저장 201, 같은 날 같은 요청 재사용 200이며 기존 `{simulation, created}`를 유지한다.

| 경로 접미사 | 입력 및 검증 | 생략값 |
| --- | --- | --- |
| saving-product | productId 양수 Long, monthlyAmount 양수 Long, term 정수 1~120 | 없음 |
| loan/new | productId 양수 Long, principal 양수 Long, term 정수 1~360, repaymentType은 Loan enum 3종 | 상품 조건으로 방식이 하나로 확정되는 경우에만 선택 |
| loan/prepayment | accountNo 숫자 10~20자리, prepaymentAmount 양수 Long, paymentDate ISO 날짜 | paymentDate=실행 기준일 |
| loan/refinance | accountNo 숫자 10~20자리, targetProductId 양수 Long, refinanceAmount 양수 Long | refinanceAmount=기준일 대출 잔액 |

- 필수 null·누락, 소수 금액/기간, 정수 범위 초과, 잘못된 enum·날짜·빈 문자열은 400이다. 선택 null은 생략과 동일하다.
- 없는 상품은 404, 존재하지만 대상 유형·옵션이 부적합하면 400이다. 없는·타인 대출은 모두 같은 404로 처리한다.
- 대출은 ACTIVE이며 잔액 양수인 건만 실행한다. OVERDUE는 연체·미납 비용을 확정할 수 없어 계산 불가다. 종료 상태·잔액 0도 실행 불가다.
- 명세에 없는 optionId, goalId, 출금계좌, 금리 입력을 추가하지 않는다. 기존 saving의 계좌번호 형식은 변경하지 않는다.
- 현금흐름 months는 다음 달부터 예적금 term개월, 대출은 만기 월까지 최대 120개월이다. 신규 대출 전체 계산은 360회까지, 보유 대출의 잔여 일정이 360회를 넘으면 POST를 거부한다. 잘린 전체 이자를 저장하지 않는다.

### 10.2 상품 옵션 선택

1. 예금은 DEPOSIT + FIXED_DEPOSIT, 적금은 SAVINGS 유형을 지원한다. 적금은 저장 기본금리에 매월 같은 금액을 납입하는 가상 모형이며 자유적립형에도 같은 납입을 가정한다. 가입 자격·특별조건 충족 여부는 판정하지 않는다. 예금의 다른 saving_type 또는 null은 지원하지 않는다.
2. 대출은 대출 ProductType과 533의 CREDIT/CREDIT_MID/MORTGAGE/JEONSE/AUTO 비교군에 속한 loan_type만 지원한다. 한도대출·마이너스통장은 제외한다. 대환은 기존 대출의 연결 상품에서 비교군을 확인하고 대상과 동일 군을 요구한다. 연결 상품이 없으면 비교군을 추측하지 않는다.
3. 예적금과 신규 대출은 option.term=요청 term을 요구한다. 대환은 기준일에 맞는 다음 약정 회차부터 만기까지의 **잔여 회차 수 n**과 option.term을 맞춘다. 기존 일정 날짜를 보존하므로 달력상 n개월 계약과 다를 수 있으며 `REMAINING_SCHEDULE_AS_TERM` 가정을 제공한다. 기간 밴드만 맞는 후보는 실행 불가다.
4. 대출 상환방식 대응: EQUAL_PAYMENT→EQUAL_PRINCIPAL_INTEREST/AMORTIZING, EQUAL_PRINCIPAL→EQUAL_PRINCIPAL/AMORTIZING, BULLET→BULLET. 방식 자동 선택은 아래 금리·한도 필터가 끝난 후보에 적용한다. 생략 시 후보들을 대응한 Loan 방식의 합집합이 한 종류일 때만 자동 선택한다.
5. 예적금은 option.rate, 대출은 option.minRate를 사용한다. null·음수 금리, minRate>maxRate는 부적합이다. 0%는 유효하다. 상품 최상위 금리로 누락을 보충하지 않는다.
6. 대출 한도는 양수 option.limitAmount와 product.maxLimit 중 작은 값이다. 둘 중 하나만 있으면 그 값, 둘 다 없으면 상한 검증을 생략한다. 요청 principal 또는 대환할 신규 대출분을 **옵션별 한도와 비교해 먼저 후보를 거른다**. 0·음수 저장 한도는 해당 옵션의 자료 오류이며 상품 공통 한도 오류는 전체 후보에 적용한다.
7. 처리 순서는 유형·기간·명시 상환방식→유효 금리·한도 자료→요청 금액의 한도 충족→생략 상환방식 확정→정렬·선택이다. 유효 조건 후보가 없다면 PRODUCT_OPTION_UNAVAILABLE, 유효 후보 모두가 알려진 한도 때문에 탈락했다면 PRODUCT_LIMIT_EXCEEDED다(코드 접두사 SIMULATION_). 금액 필터 이후에도 방식이 여러 개면 REPAYMENT_TYPE_REQUIRED다. 한도 불명 후보는 유지하고 선택됐을 때 PRODUCT_LIMIT_UNKNOWN을 표시한다.
   최종 후보가 여럿이면 대출은 모호하지 않은 상환 코드 우선, 이후 금리 오름차순·optionId 오름차순으로 선택한다. 예적금도 기본금리 오름차순·optionId 오름차순이다. 서로 다른 rate_type 중 하나를 택하면 선택된 값을 결과에 표시한다. 이는 공시 조건 중 결정적으로 선택한 가상 시나리오다.
8. 선택된 옵션 ID·term·rateType·repaymentType·공시 최소/최대금리·적용금리·syncedAt을 저장한다. 임의의 상품 유효기간은 두지 않는다. 예금·적금은 우대조건 미적용, 대출은 공시 최저금리 가정이며 승인 가능 여부를 제공하지 않는다.

### 10.3 이자·일정·금액

- 예금: 만기일=기준일.plusMonths(term), 원금=monthlyAmount. `grossInterest=floor(principal×rate×days/36500)`이며 days는 [가입일, 만기일) 실제 일수다.
- 적금: i=0..term-1에 기준일.plusMonths(i)로 납입하고 만기일은 기준일.plusMonths(term)이다. `principal=monthlyAmount×term`, `grossInterest=floor(Σ(monthlyAmount×예치일수)×rate/36500)`다. 매 회차 이자를 따로 절사하지 않는다.
- 예적금 `grossPayout=principal+grossInterest`, tax와 netPayout은 제공하지 않는다. 세전이라는 taxBasis와 EXCLUDES_TAX_AND_FEES를 표시한다.
- 대출 월이율은 연이율/1200이다. 기존 상환 계산기의 원금균등·원리금균등·만기일시 식을 재사용하고 회차 이자는 HALF_UP한다. 신규 대출 첫 회차는 기준일.plusMonths(1), 마지막은 기준일.plusMonths(term)이며 최초 일자를 약정일로 유지한다.
- 비교 이자는 동일 기준일부터 각 시나리오 만기까지의 이자 합이다. 원금 상환을 금융비용으로 합치지 않는다. `delta=after-before`, 별도 `interestSaving=beforeInterest-afterInterest`로 부호를 구분한다.
- 중도상환·대환 수수료는 계산하지 않으며 0원으로 반환하지 않는다. 전체 비용 절감액으로 명명하지 않는다.
- 금액 합계·곱셈·차이는 BigInteger 또는 exact 연산으로 검증한다. Long 범위를 넘으면 전체 실행을 거부한다. 기존 Item.amount의 단순 뺄셈을 신규 결과 생성에 그대로 사용하지 않는다.

### 10.4 추가상환과 대환 순서

추가상환:

1. 기준일 이전 nextRepaymentDate, 만기·상환일 누락, 다음 상환일>만기는 계산 불가다. paymentDate는 기준일 이상·만기 이하로 제한한다.
2. 원래 일정을 만든 후 paymentDate 이하 약정 회차는 전후 양쪽에 그대로 반영한다. 같은 날짜에는 약정상환이 먼저다.
3. 이 시점 잔액 P에 대해 0<추가상환액≤P를 검증한다. 만기 당일 약정상환으로 P=0이면 추가상환은 불가다.
4. 추가상환 후 P-A로 paymentDate 이후 원래 회차 날짜·만기를 유지해 재계산한다. 부분 상환은 각 방식에 따라 납입액을 줄이고, 전액 상환이면 이후 원금·이자는 0이다.
5. 월중 상환까지의 경과이자는 별도 정산하지 않는다. 다음 약정 회차 이자는 감소한 잔액에 월이율을 적용한다. `NO_ACCRUED_INTEREST_SETTLEMENT`와 `MONTHLY_RATE_NOT_DAILY_PRORATED`를 항상 표시한다. 이는 확정 중도상환 견적이 아니다.

대환:

1. 실행일은 기준일이다. 기존 nextRepaymentDate가 기준일 당일이면 오늘 약정상환 반영 여부가 불명확하므로 `REPAYMENT_DUE_TODAY`로 거부한다. 미래 상환일부터 남은 일정이 명확한 대출을 대상으로 한다.
2. 잔액 P에서 A를 대환한다. A=P이면 신규분만, A<P이면 기존 금리의 P-A와 신규 금리의 A를 같은 날짜·만기·상환방식으로 계산한다.
3. 총 원금은 P로 보존한다. 실행일 대환 유입 A와 상환 A는 순현금 0이며, 별도 수수료 현금 유출은 미반영이다.
4. 부분 대환의 회차별 반올림으로 같은 금리라도 1원 수준 차이가 날 수 있다. 전액·동일 금리 대환은 기존 일정과 정확히 같아야 하며 부분 대환은 두 개별 일정의 합과 일치해야 한다.

### 10.5 기준선·현금흐름·목표

- 기존 Snapshot의 monthlyIncome/monthlySpending/monthlySaving/monthlyAvailableFunds는 **참고 기준선**으로 유지한다. 신규 유형에서 대출 납입액을 monthlySpending에 끼워 넣지 않는다. before/after 공통 기준선이 같아도 유형별 변화는 comparison·cashflow에 나타난다.
- 신규 유형 cashflow.basis=`SCENARIO_NET_CASH_CHANGE`, before/after는 null이다. 사용자 전체 가용잔액을 산출하지 않았다는 뜻이다. 기존 spending/saving은 MONTHLY_AVAILABLE_FUNDS 계약을 유지한다.
- cashflow에 `currentMonth{yearMonth,delta}`를 추가하고 기준일부터 당월 말까지의 변화를 합산한다. 다음 달부터 months를 만든다. `cumulative`는 currentMonth.delta부터 누적한다. 기준일 후 같은 달 추가상환·납입도 빠지지 않는다.
- 시나리오 현금흐름: 예금 -원금/+만기수령액, 적금 -회차납입/+만기수령액, 신규 대출 +차입/-상환, 추가상환 -추가상환액+(기존상환-변경상환), 대환 기존상환-변경상환이다. 별도 이벤트 원장을 중복 합산하지 않는다.
- months 표가 120개월에서 끝나면 truncated=true, coveredThrough와 fullTermEndDate를 표시한다. 누적액은 표시기간 금액이며 만기 합계와 같다고 표시하지 않는다.
- assets/debts는 사용자 전체 합계가 아닌 **시나리오 영향액**이다. 기준일 최초 변화, 선택 행동일의 원금 이동, 만기까지의 이자 손익을 서로 다른 key로 표시한다. 예금 가입·신규 차입·추가상환의 원금 이동 자체는 순자산 변화 0이다. 미래 추가상환이면 기준일 최초 현금·부채 변화도 각각 0이며 감소액은 paymentDate에만 반영한다.
- 예적금 가입·추가상환·신규 대출은 자금 출처 또는 목표 귀속이 없어 목표별 afterForecastDate와 differenceDays를 null로 반환한다. `FUNDING_SOURCE_UNKNOWN` 또는 `GOAL_ALLOCATION_UNKNOWN`을 목표별 reasons로 표시한다. 목표가 아예 없으면 []다.
- 대환은 순원금 유출이 없으므로 **각 약정 상환일의** 상환 절감/증가분을 남은 목표 금액 비례로 기존 저축속도에 반영한다(`REPAYMENT_DELTA_ALLOCATED_TO_GOALS`). 날짜가 없는 cashflow.months 합계를 목표 계산 입력으로 쓰지 않는다. 배분 비중은 기준일 미달성 목표의 remaining으로 고정하고 goalId 순으로 정렬한다. 각 상환일의 금액을 배분할 때 마지막 목표가 나머지를 받는다. 도중 달성한 목표의 몫을 다른 목표로 재배분하지 않는다.
- 목표 투영일은 t(k)=기준일.plusMonths(k), k≥1이다. 매 구간 (t(k-1), t(k)]에 **실제로 발생하는 날짜가 포함된** 배분 delta만 모으고 구간 종료일 t(k)에 `max(0, 기존 월 저축속도+구간 delta 합)`을 반영한다. 당월의 미래 절감액도 첫 투영일까지 기다려 반영한다. 양수 절감액을 실제 발생일보다 먼저 사용할 수 없다. 음수이면 목표 원금 인출 없이 해당 구간 저축액을 0 하한 처리한다.
- remaining이 처음 0 이하가 되는 t(k)를 afterForecastDate로 반환한다. 이는 기존 월 저축속도에 맞춘 월 단위 보수적 추정(`GOAL_EFFECT_AT_NEXT_PROJECTION_DATE`)이다. 예를 들어 1/14 기준 2/28 절감액은 3/14 투영에 반영하며 2/14로 소급하지 않는다. 최초 약정일 기준 plusMonths로 말일을 복원한다.
- 마지막 상환일을 포함하는 투영 구간까지 계산한 뒤 남은 금액은 기존 속도로 필요한 개월 수를 구해 원래 t(k) 축에서 이어 계산한다. 이미 달성한 목표는 기준일, 속도 0이고 모든 예정 절감 반영 후에도 미달성이면 null이다. 변화가 모두 0이면 기존 before 날짜를 그대로 반환한다. 120개월 현금흐름 표시 상한과 독립적으로 전체 날짜별 일정을 사용한다. 기존 목표 엔티티·잔액·이력은 변경하지 않는다.

### 10.6 저장과 응답 확장

- 기존 SimulationResult는 고정 record이므로 JSON에 필드만 더할 수 없다. `details`(유형별 조건·계산치), `goalImpactDetails`(goalId/status/reasons)를 선택 필드로 추가해 Store가 after_snapshot에 저장하도록 확장한다. 기존 생성자는 오버로드로 보존하고 null 확장 필드는 생략한다.
- Cashflow는 currentMonth, truncated, coveredThrough, fullTermEndDate를 선택 필드로 추가한다. 기존 두 유형에는 새 필드를 출력하지 않는다. GoalImpact 엔티티에는 날짜만 저장하며 사유는 after_snapshot.goalImpactDetails에서 읽는다. 목표 영향 응답은 `SimulationGoalImpactResponseAssembler` 한 곳에서 엔티티 날짜와 저장 JSON의 status/reasons를 goalId로 결합한다. 실행 POST의 simulation.goalImpacts, 상세 GET의 goalImpacts, GET /goal-impact 모두 같은 조립기를 사용하고 goalId 오름차순으로 반환한다. SimulationResponse.of의 직접 엔티티 변환과 SimulationQueryService.goalImpact의 직접 변환을 함께 교체한다. 과거 저장건은 확장 필드 없이 기존 계약을 유지하며 조회 시 재계산하지 않는다.
- details에는 dataSource, taxBasis, calculationAsOfDate, 상품 스냅샷, 대상 loanId(번호 제외), 적용 조건, beforeInterest/afterInterest/interestSaving, grossPrincipal/grossInterest/grossPayout 중 해당 유형 필드만 둔다. 계산 불가 목표 사유와 전체 계산 실패를 구분한다.
- comparison 항목은 기존 `{key,label,before,after,delta}`를 유지한다. 비용 항목은 INTEREST_TOTAL, 부채는 INITIAL_DEBT_CHANGE, 자산은 INITIAL_CASH_CHANGE/INITIAL_PRODUCT_PRINCIPAL_CHANGE/INITIAL_NET_ASSET_CHANGE로 기준일 최초 변화를 표시한다. 차이액 항목의 before는 0, after는 시나리오 영향액이다.
- 추가상환 행동의 현금·부채 변화는 PREPAYMENT_CASH_CHANGE/PREPAYMENT_DEBT_CHANGE 키로 별도 제공하고 after.details.comparisonTiming에 `{key,effectiveDate,basis}`를 기록한다. INITIAL_*는 기준일·INITIAL_STATE, PREPAYMENT_*는 paymentDate·ACTION_EVENT, INTEREST_TOTAL은 기준일~만기의 PERIOD_TOTAL을 사용하며 기간 항목에는 fromDate/toDate를 둔다. 당일 상환이면 최초 변화와 행동일 변화는 같은 사건의 두 표시이므로 합산하지 않는다. 비교 항목은 집계 원장이 아니며 cashflow는 날짜별 사건을 한 번만 합산한다.
- 예: 1/1 기준 2/1에 200,000 추가상환이면 INITIAL_CASH_CHANGE=0, INITIAL_DEBT_CHANGE=0이다. PREPAYMENT_CASH_CHANGE=-200,000, PREPAYMENT_DEBT_CHANGE=-200,000의 effectiveDate는 2/1이다. 기존 약정상환은 행동 전후에 공통이므로 추가상환 사건 금액에 다시 넣지 않는다. 월 상환 전후는 MONTHLY_REPAYMENT_YYYY_MM 항목으로 items에 최대 120개월 제공한다.
- Runner 안에서 기준일 확보→사용자 잠금→번호를 본인 loanId로 정규화/날짜 기본값·요청 모드 확정→원본 리소스존재·소유권 확인→지문 조회→신규이면 상품 옵션·한도 등 자료 준비와 실제 적용값 확정→순수 계산→원자 저장한다. 지문 조회 전에는 생략된 상환방식의 자동 선택을 수행하지 않는다. 기존 두 유형의 실행 순서는 회귀 테스트로 보존한다.
- 지문은 사용자·유형·내부 ID·정규화된 요청·기준일·계산 버전으로 만든다. 상품 금리·잔액 등 변동 스냅샷은 넣지 않는다. 날짜처럼 데이터 조회 없이 결정되는 기본값은 생략과 명시를 같은 지문으로 처리한다. 신규 대출 repaymentType 생략 또는 null은 내부 요청 모드 `AUTO`, 명시는 해당 Loan enum을 지문에 넣는다. 대환 금액 생략은 기존대로 `FULL_BALANCE` 토큰을 사용한다. AUTO와 명시 방식, FULL_BALANCE와 명시 금액은 결과가 같더라도 별개 요청이다. 이 구분을 FE에 고지한다.
- 신규 AUTO 요청만 §10.2의 금리·한도 필터 이후 실제 상환방식을 확정한다. 요청 스냅샷·scenario parameters에는 생략 시 `repaymentType=null`과 `repaymentTypeMode=AUTO`를, 명시 시 입력 enum과 `repaymentTypeMode=EXPLICIT`을 저장한다. 실제 선택값은 after.details.resolvedRepaymentType과 선택 상품 옵션 스냅샷에 저장하며 요청 지문에 역으로 섞지 않는다. AUTO는 내부 모드이며 API repaymentType의 허용 enum을 늘리지 않는다. 같은 날 AUTO 재요청은 상품 옵션이 변경돼도 저장된 선택값과 결과를 재사용한다.
- 같은 날 상품이 갱신돼도 같은 요청이면 첫 저장값을 반환한다. 원본 리소스가 사라지거나 소유권 확인이 실패하면 재실행 요청은 404이며, 기존 시뮬레이션 GET은 저장값을 계속 반환한다.
- 계산 버전을 올리고, JSON 확장 필드가 없는 과거 결과 조회·삭제를 검증한다. 스키마 변경은 필요하지 않다.

### 10.7 실패 계약

아래 SIMULATION_* 코드는 신규 추가할 설계 이름이다. 기존 ErrorCode와 충돌을 확인해 같은 뜻이 있으면 재사용한다. 응답은 기존 ApiResponse 실패 형식, 민감값 없는 고정 메시지다.

| HTTP | 코드 | 조건 |
| --- | --- | --- |
| 400 | VALIDATION_ERROR / INVALID_REQUEST | 형식·범위·파싱 오류(기존 전역 매핑 유지) |
| 401 | 기존 인증 오류 | 토큰 없음·유효하지 않음 |
| 404 | RESOURCE_NOT_FOUND | 상품 없음, 대출 없음·타인 |
| 400 | SIMULATION_PRODUCT_NOT_SUPPORTED | 상품 유형·대환 비교군 불일치 |
| 400 | SIMULATION_PRODUCT_OPTION_UNAVAILABLE | 기간·방식·금리 조건을 만족하는 옵션 없음 |
| 400 | SIMULATION_REPAYMENT_TYPE_REQUIRED | 생략된 상환방식을 유일하게 선택 불가 |
| 400 | SIMULATION_PRODUCT_LIMIT_EXCEEDED | 대출분이 공시 한도 초과 |
| 400 | SIMULATION_LOAN_DATA_UNAVAILABLE | 상태·날짜·금리·만기 자료 불완전, 당일 대환 불가 |
| 400 | SIMULATION_INVALID_PAYMENT_DATE | 추가상환일 과거 또는 만기 초과 |
| 400 | SIMULATION_AMOUNT_EXCEEDS_BALANCE | 실행 시점 잔액보다 큰 추가상환·대환 |
| 400 | SIMULATION_PERIOD_NOT_SUPPORTED | 보유 대출 잔여 계산이 360회 초과 |
| 400 | SIMULATION_AMOUNT_OUT_OF_RANGE | 계산 결과나 차이가 Long 범위 초과 |

자료 누락을 500이나 성공 0원으로 바꾸지 않는다. 계산 핵심 자료가 부족하면 저장하지 않는다. 목표 영향만 부족하면 나머지 계산을 저장하고 해당 목표의 null·사유를 반환한다. 세부 이유는 details가 아닌 실패 메시지의 안전한 설명으로 구분하고 요청 계좌번호를 포함하지 않는다.

| 한도와 방식 자동 선택 | 방식 생략, EQUAL_PAYMENT 후보는 한도 미달·BULLET 후보만 금액 충족 | 금액 필터 후 BULLET 자동 선택; 방식 모호 오류 아님 |
| 미래 상환 시점 분리 | 기준 1/1, 2/1에 200,000 추가상환 | 최초 현금·부채 변화 0; 행동일 변화 각각 -200,000·effectiveDate=2/1; 1월 cashflow 변화 0, 2월에 한 번만 반영 |
| 목표 응답 경로 일치 | 정상 목표·계산 불가 목표가 포함된 신규 결과와 확장 필드 없는 과거 결과 | POST/상세 GET/goal-impact GET의 목표 배열이 날짜·differenceDays·status·reasons·정렬까지 동일. 재사용 POST도 동일 |
| AUTO 요청 재사용 | 신규 대출 repaymentType 생략으로 실행 후 같은 날 상품 옵션 변경·동일 요청 재실행 | 최초 201, 재실행 200·같은 simulationId·최초 resolvedRepaymentType 유지; 옵션 자동 선택 재실행 없음 |
| AUTO 정규화와 명시 구분 | 같은 날 동일 입력에서 repaymentType 생략→null→최초 선택된 enum 명시 | 생략과 null은 같은 건 재사용; 명시는 별개 지문으로 현재 상품 조건 검증 후 신규 계산 |

추가 검증: 목표 remaining=25,000·속도 10,000이면 위 절감으로 3개월→2개월 단축; 여러 목표 배분합 일치; 음수 절감; 목표 없음; 1/31→2/말→3/31; 윤년; 기간 1/120/360 및 상한 초과; 금리 null과 0 구분; AMORTIZING 생략/명시; 대환 후보 기간 불일치; 같은 날 생략값 재사용; 동시 요청 1건 저장; 금융 원본 행 불변; 기존 spending/saving 응답 회귀.

### 10.9 구현 단위와 완료 산출물

1. DTO/정규화·오류 및 상품 옵션 Reader: 위 입력·옵션 테스트 통과.
2. 순수 금융 계산 4종: 검산 표 및 원금 보존·날짜·오버플로 테스트 통과.
3. Runner/Store·결과 record 호환 확장과 날짜별 목표 투영: 기존 두 유형 회귀·원본 데이터 불변·동시 요청·발생일보다 빠른 목표 달성 방지 검증.
4. Controller 4경로와 공통 조회: 정상/인증/소유권/실패 무저장·JSON 왕복·공통 목표 응답 조립기 경로 일치 검증.
5. simulation.md 계약·4종 예시·오류·가정·FE 인계 갱신, H2/전체 테스트/MySQL 결과 기록.

이번 구체화 작업은 이 문서까지다. 구현 시 실제 예시 JSON은 DTO 직렬화 테스트에서 생성해 문서에 반영한다. 코드·기준 docs·FE·infra는 아직 변경하지 않았다.
