## 3. 계산 변경

### 3-1. 입출금 저축속도 목표별 안분 (승인 불필요 — 회귀 수정)

626 MR-A는 **확보액**의 목표 간 중복만 막았다. 저축속도는 694에서 따로 생겼고 안분이 없다.
[GoalSavingPaceReader](../src/main/java/com/ssafy/dodam/domain/goal/service/GoalSavingPaceReader.java) line 68-77이
그 목표의 입출금 계좌 목록으로 **순현금흐름 전액**을 가져오므로, 한 통장을 두 목표에 연결하면 두 목표가 같은 증가분을
각자 전액 센다.

```
입출금 항 = Σ over 연결 입출금 계좌 a:
              netCashflow(a, 창) / 관측개월 × share(a, goal)

share(a, goal) = 이 목표의 링크 기여액 / a의 allocatedTotal
```

- `allocatedTotal`은 `GoalAllocationReader.AccountAllocation`이 이미 계산해 `monthlyPace`가 받는 `GoalAllocation` 안에 있다.
- 지금처럼 `contribution_amount`가 전부 NULL이면 각 목표의 기여액이 잔액 전체이므로 `share = 1/연결 목표 수`,
  즉 **균등 분할이 자동으로 나온다.** 폴백을 따로 두지 않는다.
- 담기가 도입되면 `share`가 실제 배정 비율이 된다. 같은 식이 그대로 유지된다.
- 쿼리 변경: `JdbcGoalPaceReader.readNetCashflow`를 계좌 합산 → **계좌별 반환**으로.

### 3-2. 저축속도 정의 교체 (확정 2026-09-22 — 626 §6 결정을 되돌림)

626 §6은 "거래 기반 저축속도 개편은 범위 밖. **할당 증가를 저축 실적으로 간주하는 코드를 만들지 않는다**"로 닫았다.
이 계획은 그 반대를 제안한다.

```
입출금 항(현재) = 연결 입출금 계좌의 순현금흐름 평균     ← "안 쓴 돈"
입출금 항(제안) = 그 목표에 담은 금액의 증가분 / 기간     ← "떼어둔 돈"
```

되돌리자는 근거:

- 626 당시 저축속도는 `확보액 / 목표 생성 후 경과 개월`이었다. 순현금흐름 기반 정의는 694(2026-09-22)에 들어왔고,
  702에서 다시 연결 계좌로 한정해야 했다. 626이 판단할 때 없던 구조다.
- 순현금흐름은 잔액이 안 줄었다는 사실일 뿐 목표를 향한 저축이 아니다. 급여·상여·명절·카드 대금 시점이 그대로 섞인다.
- 담기는 사용자가 명시적으로 한 행동이라 "저축 실적"으로 불러도 해석이 어긋나지 않는다. 626이 경계한 것은
  *자동으로* 할당을 실적으로 바꾸는 것이었고, 여기서는 사용자 행위가 원천이다.

전환 기간 처리: 이동 이력이 없는 과거 구간은 증가분을 알 수 없다. **입출금 항을 0으로 두고 시작**해 이력이 쌓이면서
값이 생긴다. 보수적인 방향(예상일이 늦게 나옴)이므로 과대 약속이 생기지 않는다. 예·적금 항은 그대로다.

§5-2(이동 이력)가 선행 조건이다.

## 4. API

### 4-1. 담기·꺼내기 (626 §4 그대로)

```
PUT /api/v1/goals/{goalId}/allocations/{accountId}
{ "amount": 300000 }
```

- 절대값 PUT 하나로 담기·꺼내기를 모두 처리한다. 재시도·중복 탭이 자연히 멱등이고 `requestId`·멱등 테이블을 두지 않는다.
- 0은 행 삭제(할당 해제). A→B 직접 이동은 제공하지 않는다.
- 검증: `amount ≤ balance − (다른 목표 할당 합)` 하나.
- 잠금 순서: 사용자 행 → 계좌 ID 오름차순 → 목표 ID 오름차순.
- 한 트랜잭션: 소유권·SAVING·상태 확인 → 최신 잔액·총 할당액 검증 → 할당 갱신 → 확보액 갱신 → 이력.
- 오류: 401 / 타인·없는·삭제 목표·계좌 404 / 유형·입력 400 / 종료 목표 할당 증가 `GOAL_NOT_EDITABLE` 409
  (감소·0은 허용) / 할당 가능액 초과 `GOAL_ALLOCATION_EXCEEDS_AVAILABLE` 409.

### 4-2. `PUT /goals/{goalId}/accounts` 예·적금 한정 (626 §4)

- Body `accountIds[]` 유지. 입출금이 오면 검증 오류로 4-1을 안내한다.
- 빈 배열은 예·적금 연결만 해제하고 입출금 할당은 건드리지 않는다.

### 4-3. 꺼내기 영향 미리보기 (신규 제안)

626에 없던 항목이다. 꺼내기 확인 화면에서 목표 영향을 먼저 보여준다.

> 결혼 자금에서 500,000원을 꺼내면 예상 달성일이 2029-03-14 → 2029-04-26으로 **43일 늦어집니다.**

- BE 신규 계산 없음. `POST /simulations/saving`에 `goalId` + 꺼낸 뒤 월 저축액을 넣어 호출하면 된다.
- 실제 은행 세이프박스가 못 하는 부분이고, FE 화면 한 곳이다. **MR 분할상 마지막이며 빠져도 나머지는 성립한다.**

## 5. 데이터

### 5-1. 스키마 변경 없음 (담기·꺼내기 자체)

`contribution_amount`·V35 조건부 UNIQUE·복합 FK 모두 그대로 쓴다. 626 §5의 "기존 자료 전환 없음"을 유지한다 —
NULL은 계속 전액으로 읽고 사용자가 처음 담기/꺼내기를 할 때 숫자로 바뀐다. 마이그레이션 SQL을 두지 않는다.

시연 seed [DODAM_GOAL_SEED.sql](../database/seeds/DODAM_GOAL_SEED.sql)의 DEMAND_DEPOSIT 링크 1,750건도 그대로 유효하다.

### 5-2. 이동 이력 (확정 2026-09-22 — 626 §4 결정을 되돌림)

626은 "변동 이력은 기존 `goal_history` `ACCOUNTS_UPDATED`로 남긴다. **별도 할당 이력 테이블은 두지 않는다**"로 닫았다.
그대로 가면 두 가지가 막힌다.

1. §3-2의 저축속도(담은 금액 증가분)를 계산할 원천이 없다. `goal_history`는 확보액 스냅샷이고 조회할 때마다
   `AMOUNT_UPDATED`로 갱신되므로 "사용자가 얼마를 담았는가"를 복원할 수 없다.
2. 목표 상세 차트가 지금처럼 오염된다. FE가 `goal_history`를 이벤트 구분 없이 그대로 찍는데
   ([useGoalDetail.ts](../../frontend/src/pages/goalDetail/hooks/useGoalDetail.ts) line 41-67),
   연결 변경이 저축 그래프에 점프로 나타난다.

**확정: `goal_allocation_movement` 신규 테이블.** `goal_history` 확장안은 조회할 때마다 쌓이는 `AMOUNT_UPDATED` 노이즈가
차트에 그대로 남아 채택하지 않았다.

| 컬럼 | 비고 |
| --- | --- |
| `movement_id` | PK |
| `user_id`, `goal_id`, `account_id` | 복합 FK는 `goal_account`와 같은 축 |
| `amount_before`, `amount_after` | 절대값 PUT이라 둘 다 저장해야 증감을 복원한다 |
| `delta` | `after − before`. 음수는 꺼내기 |
| `occurred_at` | 저축속도 창 계산의 축 |

Flyway 번호는 **V45**(BE-A 2차 구간)로 확정했다. `goal_*`은 BE-A 테이블이고 626도 V35를 BE-A 확인 후 사용한 선례를 따른다.
[migration/README.md](../src/main/resources/db/migration/README.md) 구간표 line 49의 "다음은 V44"는 낡았으므로(V44는 697이 사용)
V45 기록과 함께 고친다. **착수 전 BE-A에게 V45 선점을 알린다.**

같은 README의 무결성 규칙 "한 Account는 하나의 Goal에만 연결하며"도 V35(626)가 이미 뒤집은 내용이라 함께 고친다.

## 6. MR 분할

전부 S15P21D105-703이며 브랜치도 `S15P21D105-703-be` 하나다. **MR을 나누는 이유는 리뷰 크기가 아니라 병합 시점이 다르기 때문이다.**

| MR | 범위 | 병합 시점 | 상태 |

| **1** | §3-1 속도 안분 + 예상 달성일 상한 + 문서 부채 3건 + 계획·FE 인계 문서 | **시연 전 가능** — 시연 숫자 불변(§7 실측) | 구현 완료(`303ba71`·`47ac756`·`d26f3ff`) |

| **3** | §5-2 이동 이력(V45) + §3-2 속도 정의 교체 | **시연 후** | 미착수 |
| **4** | §4-3 꺼내기 영향 미리보기 + 시뮬레이션 재사용 지문(626 §5) | 후순위 | 미착수 |

Jira 703의 제목·설명이 저축속도 안분 범위로 되어 있으면 세이프박스 전체를 포함하도록 넓힌다.

MR-A에 묶는 문서 부채 3건: [goal.md](goal.md) line 237(694 이전 속도 정의가 남음),
[migration/README.md](../src/main/resources/db/migration/README.md)의 "한 Account는 하나의 Goal에만 연결" 규칙과 구간표 "다음은 V44".

MR-A는 시연 전에도 안전하다. **MR-B 이후는 시연 계정의 확보액·진행률이 움직이므로 시연 후로 잡는다.**
즉 703 안에서도 A와 B는 별도 MR로 나눠 A만 먼저 병합할 수 있게 한다.

## 7. 검증

626 §9의 표를 그대로 쓰고 아래를 더한다.

| 검증군 | 추가 사례 |
| --- | --- |
| 속도 안분(§3-1) | 한 입출금을 목표 2개에 연결 → 각 목표 속도가 절반. 담은 금액이 3:1이면 3:1 |
| 속도 정의(§3-2) | 이력 없는 계정 → 입출금 항 0. 담기 30만 후 1개월 경과 → 월 30만 |
| 이동 이력(§5-2) | 담기·꺼내기·0(해제)·목표 삭제 시 이력 보존 |
| 부족 상태 | 담은 뒤 실제 출금으로 `NEEDS_ADJUSTMENT` → 신규 담기 409, 부분 꺼내기 허용 |
| MySQL | V35 조건부 UNIQUE는 H2에 없다. 신규 테이블·제약은 `*MySqlIntegrationTest`로 실측 |

MR-A는 `JdbcGoalPaceReaderMySqlIntegrationTest`로 MySQL 8.0 실측을 마쳤다(2026-09-22). 준비 절차는 remaining-work의 703 절에 있다 —
빈 스키마에 **V6을 V11 뒤로 옮겨** 마이그레이션을 올리고 Flyway는 끈다. 버전 순서 그대로면 `Failed to open the referenced table 'card'`로 멈춘다.

### MR-A가 시연 숫자를 바꾸지 않는 근거 (2026-09-22 실측)

시연 서버 U0001~U0004 전부 SAVING 목표가 1개씩이고, 목표에 연결된 입출금 계좌 중 `allocatedElsewhere > 0`인 것이 **0건**이다.
공유 입출금이 없으므로 §3-1의 `share`가 전부 1이고 속도가 그대로다. 재확인 방법:

```
GET /v1/goals?size=50                     → SAVING 목표 id
GET /v1/goals/{goalId}/accounts?size=100  → accountType=DEMAND_DEPOSIT 항목의 allocatedElsewhere
```

## 8. 남은 확인 사항

설계 결정은 2026-09-22에 모두 확정했다(문서 상단 표). 남은 것은 절차다.

1. **BE-A에 V45 선점 공유** — MR 3 착수 전. 구간표에 기록하고 팀 채널에 알린다.
2. **명세 12 변경 보고** — `PUT /accounts`가 예·적금 한정으로 바뀌고 `/allocations`가 생긴다. MR 2 시점에 보고하고,
   루트 `docs/` 수정은 명시 요청이 있을 때만 한다.
3. **FE 담기·꺼내기 화면 인계** — [safebox-fe-handover.md](safebox-fe-handover.md)를 FE 담당에게 전달하고 여력을 확인한다.
   화면이 없으면 MR 2를 병합해도 사용자에게 기능이 보이지 않는다.
4. **시연 서버 678 seed 적용** — 담기 시연의 선행 조건이다. seed는 develop에 병합돼 있으나(`66a3116`) Flyway 대상이 아니라
   수동 실행이며, 적용 전에는 목표에 입출금이 연결돼 있어 담기가 진행률을 **내린다**.
