예상 증가분은 계좌·상세 각 3건, 목표·모으기 상세 각 1건, 목표 연결 3건, `savings_payment` PAID 210건(+청약 SCHEDULED 1건), 원금 합계 **95,600,000원**이다. 목표 진행률 기본 기대값은 **63.7%**(95,600,000 / 150,000,000, 소수 둘째 자리 이하는 구현 반올림 규칙을 따른다)다. 세 적금의 PAID 합은 각 계좌 잔액과 일치해야 한다. 기존 자산에 대한 증가분으로 검증하고 사용자 전체 자산을 95,600,000원으로 단정하지 않는다.

목돈적금 78,000,000원은 원금이다. `account.balance`는 예적금 조회 계약대로 원금만 담고, 현재 FE는 목록·요약(`/v1/deposit-savings`)만 호출해 만기 예상 API를 쓰지 않으므로 "약 7,800만원"이 화면에 그대로 보이도록 이자 대신 납입 회차로 맞췄다(2026-09-21 사용자 결정, 이전 안은 70회+예상 수령액 78,025,473원). 만기 예상 API(`GET /api/v1/savings/{accountNo}/maturity-forecast`)는 별도로 계산되므로 기대값을 기록한다. `SavingsForecastCalculator`(실제 예치일수/365 단리, 이자소득세 15.4% 원 단위 절사)로 만기 2027-04-15 기준을 계산하면 예상 원금 84,000,000원, 세전이자 9,669,506원, 세액 1,489,103원, 세후이자 8,180,403원, **예상 수령액 92,180,403원**이다. 잔액 컬럼에 이자를 더해 저장하지 않는다.

**상품 연결 결정(구현 시 변경).** 계획 초안은 청약·목돈적금용 시연 `SEED` 상품을 카탈로그에 넣는 안이었으나, 상품 목록·금리 비교(`SavingsRateComparisonService`)·추천이 `source_type`을 거르지 않아 합성 상품이 4,000명 전체의 비교군에 섞이는 것을 확인해 두 계좌는 `financial_product_id` NULL로 두었다(V15·524가 허용). 계좌명이 상품명을 대신하고 `SavingsRateComparisonService`는 상품 NULL을 처리한다. 청년도약만 기존 상품에 연결한다. 계약기간을 78개월로 두면 만기일(2026-10-15)이 다음 납입일과 같아져 `SavingsScheduleCalculator`·`SavingsForecastCalculator`가 계산을 거부하므로 84개월로 잡았다. 기존 자유적금 상품을 참조하는 대안은 옵션 기간(최대 36개월)과 맞지 않아 채택하지 않았다.

상품 금리는 기존 카탈로그 및 시연 가정 출처를 기록한다. 주택청약과 목돈적금의 합성 계약금리는 실제 상품 금리로 표시하지 않는다. **청약 만기일(2036-09-15)은 합성값이다** — 초안은 만기 NULL로 두어 계산 제한을 숨기지 않으려 했으나, 만기 없는 적금이 있으면 `CashflowEventCollector`가 사용자 현금흐름 예측 전체에 `SAVINGS_INCOMPLETE_SAVINGS_TERMS`를 남기고 10월 이후 청약 납입 유출을 예정에 넣지 못해 시연 화면에 번지는 것을 확인했고, 2026-09-21 검토에서 사용자가 합성 만기를 넣는 안(b)을 택했다. 실제 주택청약종합저축에는 만기가 없으므로 이 날짜를 상품 조건으로 설명하지 않는다. 청년도약 정부기여금·비과세·우대조건, 청약 납입인정액·횟수·순위·소득공제는 현 스키마가 별도로 표현하지 않는다. `savings_payment` 납입 횟수를 청약 인정 횟수로 설명하지 않는다.

이번 증가분으로 U0003 금융자산이 약 9,560만원 늘어나므로 자산 현황·진단·리포트 등 기존 시연 기대값(633 대출, 636 소비 스토리)이 달라질 수 있다. 1단계 기준표에서 영향 화면을 함께 확인한다.

## 3-1. 예상 만기금액 조회 API (accountId 기준)

- 경로: `GET /api/v1/deposit-savings/{accountId}/maturity-forecast`. 인증 필수, `accountId`는 양의 정수. 본인 소유가 아니거나 없거나 `DEPOSIT`/`SAVINGS`가 아니면 `RESOURCE_NOT_FOUND`(404)로 타인 리소스 존재를 숨긴다.
- 계산은 새로 만들지 않는다. `DEPOSIT`은 `DepositForecastService.maturityForecast`, `SAVINGS`는 `SavingsQueryService.forecast(early=false)`의 계산 경로를 그대로 쓰고, 소유 계좌 조회만 `accountNo` HMAC 해시 대신 `(userId, accountId)`로 바꾼다. 원문 계좌번호는 요청·응답·로그 어디에도 등장하지 않는다.
- 응답은 예금·적금 공통 필드로 통일한다: `asOfDate`, `accountId`, `accountName`, `accountNoMasked`, `bankCode`, `type`, `status`(`COMPLETE`/`UNAVAILABLE`), `reasons`, `assumptions`, `principal`(현재 원금), `interestRate`, `openingDate`, `expiryDate`, `daysUntilMaturity`, `expectedPrincipal`, `expectedInterest`(세전), `tax`, `expectedNetInterest`, `expectedAmount`. 예금은 `expectedPrincipal = principal`, 적금은 납입 원금 + 남은 예정 회차 합이다. `UNAVAILABLE`이면 금액 필드는 null이고 `reasons`에 기존 사유 코드(`MISSING_EXPIRY_DATE`, `INCOMPLETE_SAVINGS_TERMS` 등)를 그대로 싣는다. 청약처럼 만기 NULL인 계좌는 `UNAVAILABLE`로 답하며 0원을 돌려주지 않는다.
- 기존 `accountNo` 경로 두 개는 유지한다. 명세 변경이 아니라 추가이며, 루트 `docs/` API 명세 갱신은 사용자에게 알리고 별도 요청 시 반영한다.
- FE 인계 스펙(FE 담당 구현, 678 BE 범위 밖): 예적금 목록 카드에 `!` 아이콘 → 탭 시 위 API 호출 → 바텀시트에 예상 수령액을 크게, 원금·세후이자·만기일·남은 일수를 보조로 표시. `UNAVAILABLE`이면 "만기일이 없어 계산할 수 없어요"처럼 사유별 문구를 보여준다. `expectedAmount`는 추정치라는 안내를 붙인다.

## 4. 구현 순서

### 1단계 — 선행 조건·시나리오 확정 (09/21)

1. 실제 작업 전 최신 `develop`과 Jira에서 생성한 `S15P21D105-678-db`의 기준을 확인한다. 현재 로컬 브랜치 목록에서 이 브랜치를 확인하지 못했으며 원격 조회도 네트워크 제한으로 실패했다. 이번 계획 작성으로 브랜치를 생성하거나 전환하지 않았다.
2. V3·V5·V7~V10·V15·V35와 최신 적용 마이그레이션, 상품 seed·491·524·493 적재 여부를 확인한다.
3. U0003, 소유한 ACTIVE 출금계좌, 기존 계좌·목표·상품의 식별값과 기준일 잔액을 읽어 적재 전 기준표를 만든다. 운영 환경 접근·적재는 인프라 담당 절차로 분리한다.
4. 세 계좌의 계약금리·개설일·만기일·납입 회차와 신규 목표를 확정한다. 청년도약 상품 자연키 조회가 0건 또는 복수 건이면 임의의 `LIMIT 1` 선택 없이 중단한다.
5. 청약·목돈적금용 합성 `SEED` 상품이 상품 조회·추천에 노출되는 영향을 점검한다. → 점검 결과 노출되므로 상품을 넣지 않는 것으로 결정(3절).

구현 조건:

- `FieldCryptor`, `SensitiveNumberHasher`, 계좌번호 masker와 같은 형식을 사용한다. 기존 대출 fixture 도구는 참고하되 원문·키를 결과 SQL·로그·문서에 남기지 않는다. AES-GCM은 매 실행 새 IV를 사용하고 재실행 식별은 안정적인 HMAC과 전용 seed 코드로 한다.
- 일반 `DATA_HASH_KEY`와 계좌번호용 `NUMBER_HASH_KEY`를 혼동하지 않는다. 실제 `SensitiveNumberHasher` 설정과 테스트로 일치 여부를 확인한다. `infra/.env`는 읽거나 수정하지 않는다.
- fixture 해시 중복, 다른 소유자·유형·기존 계좌와의 충돌, 상품 유형 불일치, 출금계좌 소유권, 신규 목표 이름·식별 충돌을 preflight에서 차단한다.
- 계좌 `source_type=SEED`, 전용 식별자와 고정 생성 시각을 사용한다. 목표는 제목만으로 갱신하지 않고 소유자·유형·생성 시각·예상 연결까지 대조한다. 사용자 수정 등 예상 상태와 다르면 중단한다.
- 신규 상품·계좌·연결은 존재 확인 후 삽입하고, 변경은 678이 소유하는 행으로 제한한다. 계좌 ID와 목표 ID가 재실행 때 바뀌지 않게 한다. 회차는 세 계좌 것만 지우고 다시 만든다(`savings_payment_id`는 바뀔 수 있으나 참조하는 곳이 없다).
- 준비용 DDL과 영구 데이터 DML을 분리하고 DML은 트랜잭션으로 처리한다. MySQL DDL의 암묵 커밋과 TEMPORARY 테이블 다중 참조 제한을 고려한다. 실패 시 계속 진행하는 `mysql --force` 사용을 금지한다.
- 기존 연결을 보존하고 신규 목표 `current_amount`만 기존 확보액 계산 계약에 맞춘다. 목표 이력을 넣으면 678 생성 이벤트 하나로 식별해 재실행 중복을 막는다.
- 납입 회차는 이력·예정의 근거이며 계좌 잔액에 다시 더하지 않는다. 312의 거래 원장 보강에 납입일·금액·계좌를 인계하고 678에서 동일한 출금 거래를 중복 생성하지 않는다.
